Hand a failed agent-initiated deploy back to the agent instead of dropping it, and keep a repair loop addressable across its redeploys. `/api/deploy` marked every deploy carrying `agentInitiated: true` as already `deployRepairing` with a `delivered` handoff state, which is only correct for a redeploy inside a repair loop the agent already owns. The `radius_deploy` tool sets that flag on every call, so a first agent-started deploy began life pre-marked as repairing, and `triggerDeployRepairHandoff` bailed out on its guard when the deploy failed: no repair prompt was ever sent and the failure was silently orphaned. Deploys started from the canvas Deploy button were unaffected. The deploy payload now forwards the attempt ID it belongs to, and the route re-validates it against the attempt the panel currently holds before touching any state, so repair-loop ownership is derived server-side and a stale repair is rejected instead of overwriting a newer deploy. A redeploy inside a loop also keeps the attempt ID it was handed rather than minting a new one, so the agent's follow-up `radius_deploy_status` call is no longer told its own attempt is inactive. The handoff delivery budget is preserved across a repair loop rather than being reset on every redeploy, so an undeliverable handoff can no longer retry without limit.
