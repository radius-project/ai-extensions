Make the Environments tab one guided flow, and stop it from acting on the user's behalf:

- **Creating an environment is a single two-step wizard.** A credential profile only ever exists in service of an environment, so New Environment now walks through choosing or creating a profile and then the environment details, instead of leaving the user to discover the ordering across two disconnected forms. Both sub-tabs keep their listings, and New Credential Profile still opens the credential form standalone, since clicking it expresses intent to manage a credential rather than to start an environment.
- **Credential profiles are create-and-delete only.** Environment creation copies concrete credential values into that environment's own GitHub variables, so nothing resolves a profile by name at deploy time; editing already reset verification and re-gated save, which made it equivalent to recreating, and renaming was the only way a profile's name could drift from the one recorded on environments created from it.
- **Both deletions confirm in an in-page dialog** rather than `window.confirm`, and deleting a profile lists the environments created from it so the effect is visible before confirming. The lookup is advisory: if it fails the dialog still opens, because a local delete should not depend on reaching GitHub.
- **A blocked environment deletion now explains itself instead of navigating away.** Deleting an environment that still has an application deployed showed the reason in a banner and then redirected to the Deployments tab two seconds later, so the explanation disappeared before it could be read. The modal now states that nothing was deleted and offers "Go to Deployments" or "Stay here"; the redirect still happens, only on the user's click.
- **Editing an environment stays in the canvas.** The edit action navigated out to GitHub's environment settings, a raw variable editor with none of the guidance, discovery, or validation the creation form has. It now reopens that form on the environment's stored values. The name is fixed while editing, and the form says why: the name is the identity the create route writes to, so typing a new one would create a second environment rather than rename this one.
- **Deploy is gated on an environment that finished being created.** Deploy went live as soon as any managed environment existed, so an environment whose credential verification had failed still looked deployable and the only way to find out was to dispatch a run against it. The deployments form, the planned pane, and the deployed app graph now label an environment that failed or is still being created, prefer a usable one by default, and keep the primary button disabled with an explanatory title otherwise. A missing status counts as not ready, so a listing that cannot say never enables the button by omission. On the Deployed tab only the deploy mode is gated, so an existing deployment stays deletable however its environment was created.
- **Discovery owns its Refresh button.** Refresh stayed enabled while discovery was already running, so an in-flight request looked identical to an idle form and a second click could land an older result last. It is now disabled for the life of the request, re-enabled when it settles including on failure, and a duplicate request for the same provider is refused. A sole cluster selects itself, and the namespace preselects `default` when the cluster offers it.
- **Status colors stay readable whatever palette the host injects.** `--rad-success`, `--rad-warning`, and `--rad-danger` were taken from the host exactly as given, and a host can keep a light status palette in a dark canvas. Each now mixes the host token toward the active text color, so the hue survives while contrast follows the theme; the reported warning case goes from 3.89:1 to 7.22:1.
