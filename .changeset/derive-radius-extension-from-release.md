"radius": patch
---

Derive the Radius Bicep extension from the installed Radius release instead of pinning the mutable `radius:latest` tag, and fail closed when it cannot be established.

When a repository does not pin `extensions.radius` itself, canvas compilation previously fell back to a hardcoded `br:biceptypes.azurecr.io/radius:latest`. That tag floats independently of the toolchain the extension installs and runs, so a graph could be compiled against a schema the installed release does not have — silently dropping valid properties or accepting invalid ones. The failure was observable: `latest` published an artifact whose container schema lacked `hosts`, so the documented `peer.properties.hosts.<container>` service wiring failed with BCP053 even though the installed release supported it, and the same fallback also shaped the planned graph a deploy renders. `radius:edge` is years stale and unusable for the same reason.

The fallback now derives the reference from the `rad` binary that will actually run the compile: `resolveRadiusExtensionRef` reads that binary's version and `radiusExtensionRefForVersion` maps it to the registry's matching `major.minor` release-channel tag, so `v0.60.0` and its release candidates both resolve to `br:biceptypes.azurecr.io/radius:0.60`. Reading the version is a local process call, so this keeps working offline and in air-gapped installations. The mutable `latest` and `edge` tags are never derived. This also aligns the extension with the `radius-app-bicep` skill, which already instructs authors to derive the tag from the installed release and to reserve `latest` for an explicitly selected edge or development release.

A repository that pins `extensions.radius` still wins outright, including one that deliberately pins `latest`; the derived reference is used only to backfill an absent pin. When no reference can be established at all — no applicable `bicepconfig.json`, or one that omits `extensions.radius`, and no readable rad release — compilation now fails with an actionable error naming the remedy rather than substituting a floating tag and validating the model against a contract it does not target. Reading the repository config is separated from assembling the effective config, so a parse failure can no longer mask that error, and the three outcomes stay distinct: a malformed config is reported as unreadable with the parse detail rather than as missing, which would otherwise send the user to create a pin they already have. This supersedes the `RADIUS_BICEP_CONFIG` fallback described in "Canvas compilation now honors the repository's applicable `bicepconfig.json` in full"; the constant is replaced by `RADIUS_EXTENSION_REGISTRY` and `RADIUS_BICEP_EXPERIMENTAL_FEATURES`.

One limitation is deliberate and documented: the `major.minor` channel tag is published at GA, so a genuinely pre-GA binary used during a release-candidate window derives a tag that does not exist yet. That is a development or `RADIUS_RAD_BINARY` scenario, the failure names the exact reference it tried, and pinning `extensions.radius` overrides it. Released binaries that self-report a prerelease string are the common case and resolve to their release channel, which is why the suffix is ignored rather than preserved.

Deriving the reference from the installed release is only sound if that release cannot change during the build, so `resolveRadForGraph` now waits for an in-flight load-time `ensureRadBinary()` reconciliation instead of returning the binary currently on disk. The warm-up publishes an upgrade by renaming it over the managed path, so a build that resolved beforehand held a path whose contents could be replaced mid-flight — pinning `bicepconfig.json` to the superseded release while compiling with the new one, which is the mismatch this change exists to remove. Reconciliation runs at most once per process, so waiting for it makes the binary stable for every later build; the resolved path is also passed into `runRadAppGraph`, so the release that is read and the process that is spawned are provably the same binary. A graph build issued during a first-run upgrade can now wait for that upgrade to finish, and a warm-up that fails still falls through to whatever is on disk, preserving offline and air-gapped use.
