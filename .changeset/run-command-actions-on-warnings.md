"radius": minor
---

Turn the terminal commands the canvas suggests into actions you can run without leaving it.

Several canvas surfaces used to stop and tell you to go run a command — sign in to Azure CLI, sign in to AWS CLI, grant the GitHub CLI a missing scope, push the current branch — with the command buried in prose. Two of them offered **Copy command**; none offered to run anything.

Those suggestions now render as a callout with the command shown verbatim, **Copy**, and **Run with Copilot**. Clicking Run asks the Copilot session to run it in the terminal you are already working in, and the callout points back at the canvas control that re-checks (Verify Credentials, Retry) once it finishes.

- The command you run is rebuilt server-side from a stable identifier through a single registry in `packages/core`, never from text the page supplied. Parameters are structurally validated identifiers only — a GUID tenant or subscription, a GitHub login, a git branch — and commands are argv arrays rather than composed shell strings, so a suggestion cannot be turned into a different command.
- A command that changes state beyond the click — a machine-wide GitHub account switch, a granted token scope, or a `git push` — asks a second time in place, naming what changes. The new `POST /api/run-remediation` route independently refuses it without that confirmation, so the guard does not depend on the page.
- The callout only claims what it can observe. It reports confirming, sending, handed off, hand-off failed, and cancelled; it never reports a success for a command it did not run. When a command cannot be built safely — an unpushable branch name, for example — Run is offered disabled with the reason stated, and Copy still works.
- The unpushed-branch suggestion now commits the generated Radius model first when it is still uncommitted. Pushing publishes commits, not the working tree, so the old single `git push` produced a branch the deploy workflow could check out but could not read a model from. The callout offers `git add` / `git commit` / `git push` over exactly the generated paths the canvas found pending, and nothing else in your working tree is staged. When nothing is pending it still offers the plain push, unchanged.
- The prompt handed to the agent stops at the command. The follow-up sentence — "return to the Radius canvas and deploy again" — is written for you and names a step in the canvas, but the agent reads the prompt too, and it was taking that step itself: asked only to commit and push a branch, it went on to run the deployment. The prompt now relays the sentence as yours and says plainly not to act on it, and nothing in the push prompt mentions deployment. Retrying the deploy stays where the callout says it is: with you, in the canvas.
- The GitHub container-registry access row now asks the registry whether there is a command to show instead of deciding for itself. It previously became visible whenever a login was detected while the command it hosted was built under a stricter rule, so a login that was present but not usable left an empty row under text telling you to run the command below. The row also no longer hand-writes the command it displays; it renders the one the registry built, which is the duplication this change exists to remove.
- `/api/azure-cli-assist` is re-implemented on the same registry with its request and response payloads unchanged, and existing error prose is untouched apart from that relayed follow-up line.
- The environment wizard's GitHub access warning is a callout too. It was the last surface still printing a whole paragraph with two commands embedded in it, and it is the one you actually reach when the signed-in account is missing `write:packages`, so the change would have looked like it had not landed. It also needed a remediation none of the existing ones expressed: switch to a named account first, then grant whichever of the workflow and package scopes that account is actually missing. The scope names are derived from the readiness check server-side rather than passed in, so the request can ask for a scope gap to be closed but cannot name the scope. When the fix is not a command at all — a missing repository grant, or an account Radius could not switch back to — the warning stays prose, because there would be nothing to run.
- That wizard warning is also no longer hidden. The fix lived inside the collapsed "View technical details" disclosure, behind a "Show how to fix" button whose only job was expanding it, so the thing you need to act on was two clicks further away than the problem statement. The fix now sits directly under the warning, and the button is gone because there is nothing left for it to reveal. "View technical details" keeps what it should have held all along: the per-check detail.
- Suggested commands are written so they run on any shell you might paste them into. A two-step command was joined with `&&`, which Windows PowerShell 5.1 — the `powershell.exe` on a stock Windows install — cannot parse; it did not gain `&&` until PowerShell 7. Multi-step commands are now one per line, which PowerShell, cmd.exe, bash, and zsh all accept, and the one place that already did this is now the only implementation. Any token containing a space is double-quoted, the single quoting form all four shells agree on.
- The instruction not to stage anything extra now travels only with the commands that stage something. It was attached to every multi-step suggestion, so the two-step `gh auth` grant told the agent to "stage only the paths named above" when that suggestion has no paths and stages nothing.
- The wizard's acting-account warning builds its command from the registry rather than writing its own. It was the last place assembling `gh auth switch ... && gh auth refresh ...` by hand, so it had the `&&` problem independently, and it could drift from the command the callout actually runs. When the account is one the registry will not build a command for, the note now says what to do instead of printing a command that would not work.
- Enterprise Managed User accounts get the callout too. A GitHub login was validated against the personal-account charset — alphanumerics and single hyphens — but an EMU login is `<shortcode>_<enterprise>`, so every EMU account failed validation, the remediation came back unrunnable, and the surface quietly fell back to the prose it was meant to replace. Because the check is shared, this silently affected the container-registry suggestion as well as the wizard. Logins may now contain underscores, while still starting and ending with an alphanumeric and staying length-bounded, so the only characters that can reach a command argument are alphanumerics, `-`, and `_`.

- Tell the agent to stop when one command in an ordered remediation fails. The displayed commands are line-separated for shell portability, which drops the stop-on-failure half of `&&`; that matters because `gh auth refresh` acts on the active account, so running it after a failed `gh auth switch` would grant the scope to the wrong account.

- Build the GitHub scope guidance in the readiness service and the GHCR write preflight from the remediation registry instead of writing the commands out by hand. The two hand-written copies had already drifted to long-form flags and would not have picked up the shell-portability fix, and each now falls back to prose rather than splicing a login the registry refuses into a command.
- Removed two newly introduced `&&` command joins on `main` (the GHCR packages-scope explainer and the credentials pane) by deriving both from the remediation registry, so the commands stay parseable in Windows PowerShell 5.1. The `github-cli-login` remediation now accepts `workflow` and `packages` opt-in booleans, and the credentials pane targets the account that actually publishes rather than the acting account.
- Render the create-environment GHCR `write:packages` failure as a Copy / Run with
  Copilot callout on the setup failure card instead of a command buried in prose.
  Only the remediation id and its params are persisted and polled; the browser
  rebuilds the command from the registry, so no command text is ever transported.
