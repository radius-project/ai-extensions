Correct the application-modeling guidance on environment variable ordering, which described a mechanism that does not exist, and enforce the real rule in the Bicep checker. Runtime composition — binding a secret into a helper variable and letting the container assemble the final value — depends on Kubernetes expanding `$(VAR_NAME)` from variables earlier in the container's environment list. The skill told the model to declare the helper first, but the containers recipe builds that list with `items()`, which sorts by key, so the order the `env` map is written in is discarded. Following the old rule produced a variable the kubelet never substituted, so the workload received the literal `$(VAR_NAME)` text as its value, and the skill's own worked example was broken by it.

The guidance now describes what the recipe actually does. The Kubernetes recipe emits `secretKeyRef` variables before plain `value` variables, so a composed value can always read a secret-backed helper regardless of naming, and that is the form to prefer. Two plain values are ordered against each other by name, so a helper supplied as a plain value — a `@secure()` parameter assigned to `env.value` — is visible only to a consumer whose key sorts after it. The skill also no longer implies the pattern is portable: the Azure ACI recipe emits every variable in one name-sorted list, and `$(VAR_NAME)` expansion is a Kubernetes container behavior in the first place.

Prose alone would leave this to be honored rather than checked, so `validate-bicep.mjs` now fails a model whose plain environment value reads a plain helper that does not sort before it, naming the resource, container, variable, and how to fix it. The check reports only what the compiled template proves: a `secretKeyRef` helper is emitted ahead of every plain value whatever it is called, and a name the container's `env` does not define may come from the image, the platform, or connection projection, so neither is flagged.
