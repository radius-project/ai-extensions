Report in-progress deploy and delete failures accurately, and clean up resources a definition no longer declares. Cancelled or timed-out runs settle every unfinished node red with the exact "Deployment cancelled" or "Deployment timed out" message while keeping the Radius error a resource already reported; a run whose state could not be saved warns that orphaned resources may exist and how to recover, including on a delete that otherwise succeeded and on the ambient deploy chip; delete confirmations list the authoritative deployed resources they will remove, or say the list is incomplete; failed, cancelled and timed-out deletes report their exact outcome on the deployments list as soon as the run ends; and resources removed from the application definition but still deployed can be deleted one by one from the deployed graph, through their own workflow, with the run followed to its outcome.

The per-resource delete only ever acts on resources the application verifiably owns, re-derives the removal from the application definition it reloads immediately before dispatching, and refuses when the branch, the definition or the deployed inventory moved in the meantime — including on the keyring-credential retry, which is re-authorized immediately before it runs and never dispatches a second time when the definition moved while the first attempt was rejected. A cleanup in flight blocks every other mutation of that deployment, including one started from another canvas instance, and a successful cleanup republishes the application's inventory from the live control plane so the deployed graph reflects it instead of the previous deploy's snapshot. A cleanup that could not persist Radius state warns on the still-deployed application's own row, with a link to the cleanup run, so the warning survives reopening the page.

Every delete dispatch carries a unique correlation id that the workflow echoes into its run name, and the run it started is resolved by that id (plus a pre-dispatch run-id baseline) rather than by "the newest run in a time window" — so a delete of another environment running at the same moment is never linked or reported as this one, and an unresolvable run is reported as unknown instead. The Deployments page follows the exact run the dispatch returned, so a retried delete no longer stops on the previous attempt's failure.
