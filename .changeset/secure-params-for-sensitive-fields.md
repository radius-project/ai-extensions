**Fixed:** Generated `app.bicep` no longer hardcodes a credential into a sensitive schema field that is not a top-level property. Guidance classified credentials only across a resource's own properties, so `Radius.Data/mySqlDatabases.password` was supplied from a `@secure()` parameter while a sensitive value nested deeper was not recognized as one — most importantly `Radius.Security/secrets.data.<key>.value`, which holds the credential even though the `data` property enclosing it is not itself marked sensitive. Sensitivity is now read through the whole resolved schema, covering a nested leaf, a property that compiles to a `secureObject` and takes one secure parameter, and the same fields on custom resource types a modeling run authors, whose `x-radius-sensitive` flags are compiled into the published extension. The rule for what may be assigned is stated explicitly: only a `@secure()` parameter referenced by name, never a literal, a parameter declared without `@secure()`, or a string interpolation, so a credential-bearing value such as a connection URL is composed where it is consumed rather than in Bicep.

**Fixed:** A secure-value violation no longer fails a modeling run without saying how to repair it. Radius reports these findings with no severity, so the checker printed them as a `warning` that nonetheless failed the build, and the underlying message named the rejected property without naming a remedy. The checker now attaches the fix to `use-secure-value-for-secure-inputs`, `secure-secrets-in-params`, and `secure-parameter-default`, so a repair attempt is spent on the correction rather than on rediscovering the rule.
