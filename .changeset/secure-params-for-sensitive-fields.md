**Changed:** Application modeling guidance now derives secure values from the whole resolved schema rather than only a resource's own properties. A sensitive field is not always a top-level one: `Radius.Security/secrets.data.<key>.value` holds the credential while the `data` property enclosing it is not itself marked, so guidance that classified credentials one level deep did not describe the shape that most often carries a secret. The rule is now stated for a nested leaf, a property that compiles to a `secureObject`, and the same fields on custom resource types a modeling run authors, whose `x-radius-sensitive` flags are compiled into the published extension. It also states what may be assigned: only a `@secure()` parameter referenced by name, never a literal, a parameter declared without `@secure()`, or a string interpolation. A value that must combine a credential with other parts, such as a connection string, is not assembled in Bicep — its parts are bound separately and composed only through a path the pinned application source proves it supports, and the contract gap is reported when it supports none.

**Changed:** A secure-value violation now explains how to repair it. Radius reports these findings with no severity, so they printed as a `warning` that nonetheless failed the build, and the message named the rejected property without naming a remedy. `use-secure-value-for-secure-inputs`, `secure-secrets-in-params`, and `secure-parameter-default` now carry the fix, so a repair attempt is spent on the correction rather than on rediscovering the rule.
