**Changed:** Application modeling guidance now states sensitivity as a rule about the schema node rather than a list of known cases. Guidance already required a `@secure()` parameter for a sensitive property and for a value placed in an authored `Radius.Security/secrets` resource, but named those two cases specifically, so a sensitive field in any other shape was left to inference: a leaf nested inside a plain object, a property that compiles to a `secureObject` and takes one secure parameter, and the same fields on custom resource types a modeling run authors, whose `x-radius-sensitive` flags are compiled into the published extension and enforced exactly as a predefined type's are. Guidance also now states what may be assigned once a node is marked — only a `@secure()` parameter referenced by name, never a literal, a parameter declared without `@secure()`, or a string interpolation, including one whose operands are all secure.

**Changed:** A secure-value violation now explains how to repair it. Radius reports these findings with no severity, so they printed as a `warning` that nonetheless failed the build, and the message named the rejected property without naming a remedy. `use-secure-value-for-secure-inputs`, `secure-secrets-in-params`, and `secure-parameter-default` now carry the fix, so a repair attempt is spent on the correction rather than on rediscovering the rule.
