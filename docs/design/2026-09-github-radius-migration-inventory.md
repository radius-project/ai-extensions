# GitHub Radius library migration inventory

## Baseline and evidence

This is stage 0 of the [implementation plan](./2026-09-github-radius-implementation-plan.md) for the [approved design](./2026-09-github-radius.md), not a new API specification. Source inspection is based on `c1c9e938963bbca923984138c82173ec3f0d8b08`; the sample implementation was not used. Refresh the affected entries before each extraction.

**Source-traced** means the behavior was traced through the linked implementation, not demonstrated against live infrastructure. **Test-backed** identifies a concrete checked-in assertion; execution evidence is recorded separately at the end. Tests with controlled dependencies do not prove that GitHub or a cloud provider accepts a real operation. Where deeper characterization is deferred, that does not waive the owning stage's safety requirements.

Except for the bounded [Stage 1A extraction](#stage-1a-workflow-observation), capabilities below remain **not migrated**. The current owner is the named module/symbol, not a new team assignment. Stage 0 introduced no migration forwarders; the Stage 1A record below now inventories the compatibility surface.

The [route table](../../packages/adapter-canvas/src/server/route-table.ts), [runtime declarations](../../packages/adapter-canvas/src/runtime/declarations.ts), and [composition root](../../packages/adapter-canvas/src/extension.ts) are authoritative for entry points. Do not reuse historical route counts from design documents. The [test plan](./2026-08-radius-canvas-test-plan.md) identifies deploy status as TL-10/RU-12 and the deployment route family as RF-07; some existing test descriptions retain older labels.

## Identity, credentials, and Azure automatic setup

**Entry points and owner (source-traced).** `GET /api/github-identity`, `POST /api/github-account`, `GET /api/credential-profiles`, and `POST /api/save-credential-profile` / `delete-credential-profile` are owned by [identity-profiles.ts](../../packages/adapter-canvas/src/server/routes/identity-profiles.ts). Provider login/assistance is exposed through `POST /api/verify-azure-login`, `verify-aws-login`, and `azure-cli-assist`; discovery uses `POST /api/discover` and Azure app-listing/consumer-read routes in the route table. `POST /api/azure-auto-setup` calls [handleAzureAutoSetup](../../packages/adapter-canvas/src/server/routes/azure-auto-setup.ts).

**Inputs, authorization, and side effects (source-traced).** Repository/provider, selected GitHub login, cloud identity and cluster details are combined with trusted runtime credentials. [createGitHubAccountCoordinator](../../packages/adapter-canvas/src/server/services/github-account-coordinator.ts) serializes selected-account work, carries `instanceId`/optional `operationId` lease metadata, and reports account restoration failures instead of assuming restoration. Azure setup separates [application selection/creation](../../packages/adapter-canvas/src/server/routes/azure-auto-setup-application.ts) from [credential and role configuration](../../packages/adapter-canvas/src/server/routes/azure-auto-setup-credentials.ts), using [OIDC helpers](../../packages/adapter-canvas/src/azure-oidc.ts), [app-create continuation](../../packages/adapter-canvas/src/azure-app-create-continuation.ts), and [credential provenance](../../packages/adapter-canvas/src/credential-provenance.ts).

**State, results, interactions (source-traced).** [Server dependency binding](../../packages/adapter-canvas/src/server/azure-auto-setup-dependencies.ts) connects provider calls to operation progress, checkpoints, identity/profile storage, and user/agent assistance. Provider mutation recovery and selected-account context are existing behavior, not a new library store. The frontend collects identity choices and permission/continuation decisions. Stop requests are observed at mutation boundaries, not treated as rollback of a command already running.

**Existing evidence.** [Azure setup unit tests](../../packages/adapter-canvas/src/server/routes/azure-auto-setup.test.ts), [HTTP setup tests](../../packages/adapter-canvas/test/integration/http/azure-auto-setup.test.ts), [identity HTTP tests](../../packages/adapter-canvas/test/integration/http/identity-profiles.test.ts), and [account coordinator tests](../../packages/adapter-canvas/src/server/services/github-account-coordinator.test.ts) are the owning suites. Deeper cross-module mutation ordering and no-panel lease/lifecycle behavior are **not newly characterized in stage 0; stage 2 must map their assertions before extraction**.

## Environment creation, publication, and verification

**Entry points and owner (source-traced).** `POST /api/operations` starts the tracked flow through [operation routes](../../packages/adapter-canvas/src/server/routes/operations-status.ts) and the server's `runEnvironmentOperationWorkflow` binding. The server-owned `POST /api/create-environment` delegates to [handleCreateEnvironment](../../packages/adapter-canvas/src/server/routes/create-environment.ts). `GET /api/verify-status`, `POST /api/bypass-verification`, and `POST /api/app-params` are owned by [environments.ts](../../packages/adapter-canvas/src/server/routes/environments.ts). There is currently no independent environment-setup tool; the shipped skill opens the wizard.

**Target and admission (source-traced; selected checks test-backed).** Inputs include repository, environment, provider/cloud settings, branch/publication context, operation continuation, and profile selection. The [refusal ladder](../../packages/adapter-canvas/src/server/routes/create-environment-refusals.ts) checks the server-owned request before body processing, then target, continuation/admission, durable registration, and namespace claims before mutations. Namespace reads use the operation's selected GitHub executor. The environment's canonical name, repository/account context, and created/reused provenance must survive downstream writes.

**Sequence and result (source-traced).** [Environment-operation coordination](../../packages/adapter-canvas/src/server/services/environment-operation.ts) performs repository-admin and package-scope preflight and environment resolution. The create route checkpoints environment/variable changes, GHCR bootstrap and provider configuration, publishes workflow files or a setup PR, and coordinates verification. Its HTTP response is a single synchronous result rather than an early acknowledgement followed by untracked writes. A successful verification dispatch is not proof of ready credentials or a successful deployment. Protected-branch and automatic-verification outcomes can require further user action.

**Identity, persistence, cancellation (source-traced).** Operations persist mutation/verification evidence; failures to checkpoint can stop subsequent writes. Cooperative stop is checked between mutations. `handleVerifyStatus` validates operation target and saved GitHub login/dispatch identity, uses its selected executor, and rejects stale retry observations. Legacy requests can still fall back to `CanvasState.verifyRunId`; a missing run ID remains pending rather than adopting the newest run. `deployDispatchedAt` and other view fields also couple the setup path to a panel. Preserve the existing intentionally combined verification/deployment path rather than interpreting extraction as configuration-only.

**Test-backed examples.** [Create-environment HTTP tests](../../packages/adapter-canvas/test/integration/http/create-environment.test.ts) assert the server-owned gate, namespace refusal, account-pinned reads, synchronous response, dispatch without claiming readiness, canonical-name propagation, persistence before later mutations, protected-branch publication, and ambiguous verification dispatch without blind redispatch. [Verification HTTP tests](../../packages/adapter-canvas/test/integration/http/environment-verify-status.test.ts) own run/status behavior. **Stage 2** must characterize panel-independent completion, interactions, and the full composite flow before shipping its tool.

## Operation storage, controls, and rollback

**Entry points (source-traced).** `GET /api/operations`, `GET /api/operations/…`, and `GET /api/operations/:operationId/diagnostics` expose records/diagnostics. `POST /api/operations/:operationId/resume/:code`, `abandon`, and `dismiss` are in [operations-status.ts](../../packages/adapter-canvas/src/server/routes/operations-status.ts). `POST /api/operations/:operationId/stop`, `continue`, `cancel-workflow`, `rollback`, `exit`, and `retry/:retryKind` belong to [operations-control.ts](../../packages/adapter-canvas/src/server/routes/operations-control.ts).

**Owner and safeguards (source-traced).** [operations.ts](../../packages/adapter-canvas/src/operations.ts) owns record transitions, admission, journal/cleanup progress, retry eligibility, and client projection. [operation-store.ts](../../packages/adapter-canvas/src/operation-store.ts) reads/writes the existing version-1 envelope and reports invalid/unavailable storage. [server.ts](../../packages/adapter-canvas/src/server.ts) composes rollback, workflow cancellation, provider reconciliation, and the shared GitHub-environment deletion primitive. Continue, rollback, exit, abandon, and deletion retry are distinct decisions, not interchangeable retries. Cleanup must respect recorded ownership and unresolved provider/workflow state.

**Lifecycle and interactions (source-traced).** [Canvas close](../../packages/adapter-canvas/src/runtime/create-radius-canvas.ts) checks `hasActiveEnvironmentTasks`, registers `onEnvironmentTasksSettled`, and bounds deferred close before `markEnvironmentInstanceShuttingDown`. This is not an independent runtime owner. UI control requests carry operation identity and admission protections; destructive/cleanup choices remain user interactions. Closing a view, requesting a stop, cancelling a remote workflow, and rolling back resources do not mean the same thing.

**Test-backed examples.** [HTTP operation controls](../../packages/adapter-canvas/test/integration/http/operations-control.test.ts) cover stop/continue/rollback on the same record, exact persisted workflow cancellation before cleanup, rejected unproven panel requests, and deletion exposing only retry. [Store tests](../../packages/adapter-canvas/src/operation-store.test.ts) and [Canvas lifecycle tests](../../packages/adapter-canvas/src/runtime/create-radius-canvas.test.ts) remain evidence owners. No store migration or stronger restart durability is introduced here. **Stage 2, then stage 6**, must test any new owner-key mapping against existing records.

## Deployment admission and dispatch

**Entry points and ownership (source-traced).** `radius_deploy` in [create-radius-tools.ts](../../packages/adapter-canvas/src/runtime/create-radius-tools.ts) selects an entry using [deploy-tools.ts](../../packages/adapter-canvas/src/deploy-tools.ts) and posts to `POST /api/deploy`. [createDeployRequestService](../../packages/adapter-canvas/src/server/services/deploy-request.ts) performs admission and launches the [monitor](../../packages/adapter-canvas/src/server/services/deploy-monitor.ts); [createDeployDispatchService](../../packages/adapter-canvas/src/server/services/deploy-dispatch.ts) prepares commands/workflows and dispatches. [server.ts](../../packages/adapter-canvas/src/server.ts) binds these factories to real helpers.

**Identity and side-effect order (source-traced).** Repair-loop validation precedes mutation/reservation; local admission precedes persisted deployment checks; branch resolution precedes synchronous `beginDeployAttempt`. The response follows background-monitor launch. A named tool attempt must match its target snapshot. Unbound calls currently select the most recently started deploy, then an available instance; that is not a proof of an unambiguous target. Missing branches can reach default-branch/legacy fallback behavior. These current selection rules need explicit treatment in stage 3 rather than silent strengthening during a move.

**Execution boundary (source-traced).** Dispatch checks source reachability and provider/OIDC preconditions, constructs existing allowed Radius commands, separates secret/public parameters, synchronizes workflows, captures available run-discovery baseline, dispatches, then invalidates listing caches. Timeout/unknown acceptance prevents credential-fallback redispatch. The request/monitor path writes attempt, run, log, progress, and repair state into `CanvasState`; deployment attempt state is not the durable environment-operation envelope.

**Tests and migration constraint.** [Request tests](../../packages/adapter-canvas/src/server/services/deploy-request.test.ts), [dispatch tests](../../packages/adapter-canvas/src/server/services/deploy-dispatch.test.ts), and [deployment HTTP tests](../../packages/adapter-canvas/test/integration/http/deployments.test.ts) own admission and dispatch assertions. Monitor transcript tests cover the current external-call order with fakes. **Stages 3a/3b** must establish one runtime-owned attempt and shared reservation before removing the server prerequisite; stage 0 does not do so.

## Workflow observation and diagnostic projection

### Stage 1A workflow observation

**Owner and scope:** Nell Shamrell-Harrington; [#887](https://github.com/radius-project/ai-extensions/pull/887) is one behavior-preserving extraction PR. [`workflow-observation.ts`](../../packages/core/src/workflow-observation.ts) owns one-shot normalization of an explicitly identified run. [`workflow-diagnostics.ts`](../../packages/core/src/workflow-diagnostics.ts) owns failed-step selection, Azure Login isolation, enterprise-claim guidance, Radius excerpts, auth-drift interpretation and terminal failure collection. Collection consumes the observed conclusion/steps; it never rereads the run, dispatches, discovers another execution, authors files or starts repair.

[`workflow-reads.ts`](../../packages/adapter-shared/src/workflow-reads.ts) owns command argv, JSON decode, combined status/jobs fallback and the minimal selected authorization helper closure. Its injected runner has no credential/account-selection responsibilities. Detail reads retain 15-second timeouts; logs retain 30 seconds and a 20 MiB buffer. A missing selected run stops fallback after the existing repository-access probe. Ambient errors remain null/fallback without selected-account probes, and log stdout never becomes CLI authorization evidence. Shape acceptance is unchanged, including permissive job/step handling; stricter validation is not part of 1A.

**Canvas adoption and residual ownership:** `server.ts` binds the existing `getRunDetail`/`fetchRunLog` signatures into deployment and selected verification. The monitor still dispatches/discovers/polls, tracks progress/heartbeat and owns attempt timing. The outcome service now calls core collection and no longer contains the moved failure interpreter. Canvas retains artifact/cache readers, graph retries/projection, resource messages/portal links, narration and repair/notification triggers. Terminal ordering remains final graph, forced progress, completion timestamp, diagnostic reads, error/resource/error-kind publication, then `failed`. Success remains attempt `complete` and resource `success`. Tool projection, named-attempt selection and tool-boundary fencing remain unchanged.

**Preserved limitations:** Deployment reads still use ambient GitHub execution; only existing verification reads use the selected executor. No new prior-verification evidence is supplied by Canvas. Null run logs retain normal failure text and continue to the best-effort control-plane read; unexpected run-log throws yield the existing degraded message. Control-plane tails remain 40 lines and Radius excerpts remain bounded. Diagnostic narration now returns after both evidence reads, so its text/order are unchanged but the failure-detail lines can appear later while the control-plane read completes. Stage 1B owns evidence-precedence corrections, 1C owns artifact extraction/validation, and 1D owns retries.

**Compatibility surface and removal condition:** `deploy.ts` re-exports `extractErrorLines`, `extractGitHubActionsStepLog`, `explainOidcEnterpriseClaim`, `extractRadDeployError`, `classifyDeployCloudAuthDrift` and `DeployCloudAuthDriftInput` from core. It re-exports the single `SelectedGhAuthorizationError` constructor, its predicate, rate-limit predicate and `selectedCommandAuthorizationError` from shared. Its `getRunDetail`/`fetchRunLog` wrappers only bind execution and delegate; discovery reuses shared `selectedWorkflowJson`. Remaining callers are `server.ts` (deployment/verification/delete composition), `server/services/verification-retry-runner.ts` through injected dependencies, `deploy.test.ts`, `server/routes/environments.test.ts`, `server/services/verification-retry{,-runner}.test.ts`, and `test/integration/http/environment-verify-status.test.ts`. `explainNoSubscriptions`, repository setup guidance and discovery policy remain Canvas-owned. Remove each forwarder only when its callers have migrated to their later-stage owner; remove the reader wrappers only after their ambient/selected host bindings have a replacement. Preserve constructor identity through that migration.

**Checked-in evidence:** Collocated core/shared tests move the existing pure and selected-reader cases with their owners and add acceptance/fallback/error matrices. The shared non-Canvas caller uses real core/shared functions and a strict ambient runner. Canvas monitor tests use those same implementations for success and failure, checking external-read order and complete publication before failure. Loopback deployment/verification contracts exercise real reads and preserve repair versus passive notification. Existing runtime tests retain status projection and named-attempt selection. Executable ESLint fixtures and a TypeScript-resolved entry-closure check enforce core/shared boundaries, including a forbidden intermediate-module fixture; both run in the existing Vitest gate.

## Repair, notices, and passive notification

**Behavior and ownership (source-traced; selected checks test-backed).** `GET /api/deploy-status` invokes `triggerDeployRepairHandoff` and `triggerDeployFailureNotice`; therefore polling `radius_deploy_status` can indirectly initiate agent work. The monitor completion path also invokes those triggers. The [server trigger functions](../../packages/adapter-canvas/src/server.ts) hold eligibility, delivery/retry, and attempt-state decisions; [runtime extension callbacks](../../packages/adapter-canvas/src/runtime/create-radius-extension.ts) connect them to the agent session. Run-unconfirmed failures use an informational notice rather than repair. Repair must remain bound to its snapshot/attempt budget.

**Passive endpoint.** `GET /api/deploy-notification` returns a smaller no-store payload: attempt/generation/run identity, status, application/environment, error, URL, repairing flag, and completion time. It does not include full resources/logs or initiate repair/notice delivery. The strengthened [HTTP notification case](../../packages/adapter-canvas/test/integration/http/deployments.test.ts) makes both callbacks throw if invoked. [Route unit tests](../../packages/adapter-canvas/src/server/routes/deployments.test.ts) and [server trigger tests](../../packages/adapter-canvas/src/server.test.ts) retain decision-level coverage.

**Lifecycle gap.** Trigger state and callbacks still depend on an entry and instance ID; closing/removing that entry is not an independent attempt lifetime. **Stages 3a/3b** own the attempt owner, explicit shared repair policy, and deduplication across tool/view observers. Read-only library observation in stage 1 must not inherit these side effects.

## Graph reads, source references, and comparison

**Entry points (source-traced).** `POST /api/load-graph`, `plan-graph`, and `diff-branches` use [graph write routes](../../packages/adapter-canvas/src/server/routes/graphs-planning-writes.ts) and [createGraphPlanningWorkflows](../../packages/adapter-canvas/src/server/routes/graph-workflows.ts). `GET /api/progress`, `deployed-graph`, and `load-graph-stream` use [graphs-planning.ts](../../packages/adapter-canvas/src/server/routes/graphs-planning.ts). `radius_generate_pr_diff_markdown` uses [runtime graph context](../../packages/adapter-canvas/src/runtime/graph-context.ts), shared graph helpers, and managed `rad`. Actions `get_graph_resources` and `update_source_refs` are declared in the runtime and operate on view-specific resources/context.

**Sources and side effects (source-traced).** [graph-pipeline.ts](../../packages/adapter-canvas/src/server/routes/graph-pipeline.ts) coordinates definition/artifact access, compilation, enrichment, and cleanup through injected helpers; core owns existing transforms and comparison. Current workflow requests still carry `instanceId`/raw body and return HTTP-shaped outcomes. Canvas state stores progress, generation/cache keys, and source-reference tokens; planned requests and handoffs check currency before mutating newer view state. Combined routes can request authoring or repair; the future pure-read API must separate that composition explicitly.

**Known source gap (source-traced).** Runtime `fetchBicepForBranch` first tries the matching workspace, then remote content when local content is falsy. The PR-diff tool describes committed models but calls that workspace-aware helper. Core's current GitHub port also collapses some failures to `null`/empty collections. Thus neither committed-only PR comparisons nor absence-versus-error semantics should be claimed as already delivered. Stage 4 must distinguish ordinary workspace-aware comparisons from committed PR comparisons, without silently falling back to remote copies of missing local files.

**Lifecycle, errors, and evidence.** Stale-token/generation guards are source-traced; they are not a guarantee that every in-flight subprocess is cancelled. [Graph workflow unit tests](../../packages/adapter-canvas/src/server/routes/graph-workflows.test.ts), [pipeline tests](../../packages/adapter-canvas/src/server/routes/graph-pipeline.test.ts), [graph HTTP writes](../../packages/adapter-canvas/test/integration/http/graphs-planning-writes.test.ts), [stream HTTP tests](../../packages/adapter-canvas/test/integration/http/graphs-planning-stream.test.ts), and [source-reference tests](../../packages/adapter-canvas/src/source-refs.test.ts) own detailed evidence. Full source/absence/staging-order characterization is **not newly delivered here; stage 4** maps and fills it. A planned graph is expected recipe output, not an authoritative cloud execution plan; environment-specific registration lookup remains separate feature work.

## Application authoring, validation, and publication

**Entry points and ownership (source-traced).** `radius_generate_app` checks available application-source evidence and returns the existing skill handoff, not a deployed application. [createAppModelHandoff](../../packages/adapter-canvas/src/runtime/app-model-handoff.ts) classifies missing/stale models, uses current-context guards, and deduplicates agent interaction. `radius_report_modeling_failure` validates instance/repository/branch/attempt token, caps error text, rechecks source/token after awaits, and returns `recorded` plus an error when stale. Runtime hooks and graph flows intentionally compose these interactions.

**Validation/publication boundary (source-traced).** The [authoring skill](../../extensions/radius/skills/radius-app-bicep/SKILL.md) and [promotion script](../../extensions/radius/skills/radius-app-bicep/scripts/promote-app-model.mjs) own staged output and managed-file replacement safeguards. `radius_publish_custom_type_extension` resolves confined `.radius`/staging paths and calls managed local extension compilation; `radius_publish_recipe` validates repository-scoped GHCR target and uses package credentials for publication. [publish-targets.ts](../../packages/adapter-canvas/src/publish-targets.ts) owns path/target validation. A completed agent response is not proof of validated files, authorization to overwrite them, or a successful deployment.

**State and interactions.** Modeling activity, claims, attempt tokens, source/skill freshness, and failure fences span runtime and Canvas state; explicit refresh can release a concluded failure for retry. The host supplies skill execution and permission/confirmation interactions. [Handoff tests](../../packages/adapter-canvas/src/runtime/app-model-handoff.test.ts), [runtime tool tests](../../packages/adapter-canvas/src/runtime/create-radius-tools.test.ts), [promotion tests](../../packages/adapter-canvas/src/promote-app-model.test.ts), and [validation integration](../../packages/adapter-canvas/test/integration/runtime/app-bicep-check.test.ts) are existing evidence owners. ## Environment deletion and retry

**Admission (source-traced).** [handleDeleteEnvironment](../../packages/adapter-canvas/src/server/routes/environments.ts) owns `POST /api/delete-environment`: it validates target presence, rejects active deletion, fails closed on unreadable deployed-application checks or target discovery, blocks remaining applications, and refuses non-Azure providers. It durably registers an operation before background work and responds `202`; an existing conflict returns `409`, unsupported provider `400`, and unavailable preconditions `503`. Target discovery supplies immutable repository/tenant/client identity used later.

**Sequence (source-traced; test-backed ordering).** [runEnvironmentDeletion](../../packages/adapter-canvas/src/server/services/environment-deletion.ts) persists stages and heartbeat activity, confirms Radius environment teardown while credentials still exist, then performs provenance-checked federated credential cleanup, GitHub-environment deletion, and state-package deletion. App registrations remain in place. Provenance/live revalidation and the shared lock protect credential ownership; missing or unconfirmed evidence cannot authorize deletion. Failure to confirm the first stage stops later cleanup and returns partial failure. State-package failure remains retryable without replaying completed earlier stages.

**Persistence and interaction.** The existing operation record stores completed/unresolved stages; retry reopens that record and resumes unresolved work. Deletion has retry rather than setup's stop/continue/rollback controls. The frontend confirms the destructive request and presents retained-credential or partial-completion guidance. Shared helpers include [GitHub environment deletion](../../packages/adapter-canvas/src/server/services/github-environment.ts), also used by setup rollback, and [state-package deletion](../../packages/adapter-canvas/src/server/services/state-package-deletion.ts).

**Test-backed examples.** [Deletion runner tests](../../packages/adapter-canvas/src/server/services/environment-deletion.test.ts) assert ordering, lock scope, first-stage fail-closed behavior, unchanged/shared/unproven credential retention, live identity revalidation, missing package convergence, and retryable package failure. [Environment HTTP tests](../../packages/adapter-canvas/test/integration/http/environments.test.ts) own admission and [operation-control HTTP tests](../../packages/adapter-canvas/test/integration/http/operations-control.test.ts) own retry projection. **Stage 6** supplies the no-panel tool path and maps close/shutdown behavior before moving this policy.
