## Stage 2A admission, checkpoint and safe-stop policy

**Scope:** This implementation candidate extracts a bounded policy seam, not the environment setup coordinator or tool entry points. [Core admission](../../packages/core/src/setup-admission.ts) owns target/default resolution, continuation eligibility, fresh-operation admission, persistence-before-namespace ordering, ownership of refused records and entering configuration only after namespace acceptance. Its typed operation snapshot and ports describe only the fields and transitions this caller uses. A pending `inputRequired` interaction blocks continuation; host input collection and Azure continuation validation stay with their existing adapter owners until the provider slice. No speculative interaction protocol, public library subpath, runtime owner, workflow format or persisted record schema is introduced.

[Core boundary policy](../../packages/core/src/setup-boundary.ts) distinguishes saved, persistence-failed and rollback-pending checkpoints and coordinates cooperative stop through typed mutation, persistence and terminal-publication ports. A live rollback decision is read after saving; failure never permits the next write. An unsettled provider mutation keeps reconciliation in charge rather than allowing Stop to strand it. Terminal notification follows successful persistence; the existing notification-error reporting boundary is preserved. These result discriminants are internal boundary decisions, not new operation states or a tool status vocabulary.

**Canvas adoption:** [Create-environment admission](../../packages/adapter-canvas/src/server/routes/create-environment-refusals.ts) immediately calls core. It retains namespace execution through the operation's selected account, HTTP refusal status/body mapping, diagnostics and failure finalization. The server-owned gate remains before request-body reading in the existing route. [Checkpoint bindings](../../packages/adapter-canvas/src/server/services/setup-checkpoint.ts) translate core decisions to the existing boolean/finalization contract; [stop bindings](../../packages/adapter-canvas/src/server/services/operation-stop-boundary.ts) retain the existing operation transitions and narration. The existing registry, provenance ledger, rollback commands, identity selection, store, task ownership and panel lifecycle are unchanged.

**Compatibility forwarding:** `server.ts::persistMutationCheckpoint` and `persistBestEffort` are behavior-free exports of `server/services/setup-checkpoint.ts`. Their current composition-root, `operations-functional.test.ts` and create-environment HTTP callers remain supported; Nell owns removal only when all imports use the service directly. The old create-environment operation/start type names reuse core contracts while preserving their exported names. Routes and stop bindings intentionally remain adapters, not temporary forwarding implementations.

**Checked-in evidence:** [Core admission tests](../../packages/core/src/setup-admission.test.ts) supply a direct non-Canvas caller and assert call order, refusal ownership, missing/default targets, both continuation stages, pending input, stale/terminal/mismatched context, canonical versus requested environment, persistence failure and dependency rejection. [Core boundary tests](../../packages/core/src/setup-boundary.test.ts) assert saved/error precedence, live rollback decisions, unsettled mutation deferral, save-before-notification and callback failure propagation. [Canvas admission tests](../../packages/adapter-canvas/src/server/routes/create-environment-refusals.test.ts) retain exact HTTP mappings and namespace identity cases. Their versioned-record matrix follows production decoding and reconciliation: versions 1 through 4 without a journal are quarantined; versions 5 through 8 interrupted during setup require the existing explicit restart decision. All are refused without claims, persistence or stage progress, preserving the recovered identity and artifacts rather than bypassing recovery. The matrix relabels current-shape records to isolate version policy; a separate minimal version-1 fixture without modern control or provenance verifies actual legacy-shape quarantine. Version alone never authorizes continuation. [Checkpoint tests](../../packages/adapter-canvas/src/server/services/setup-checkpoint.test.ts), existing stop tests, [functional persistence tests](../../packages/adapter-canvas/src/operations-functional.test.ts) and [direct-service configuration orchestration tests](../../packages/adapter-canvas/src/server/services/configure-environment-orchestration.test.ts) retain real adapter failure/cancellation contracts. ## Stage 2B runtime task ownership

**Production composition:** `extension.ts` constructs one [environment execution owner](../../packages/adapter-canvas/src/runtime/environment-execution-owner.ts), independently of the replaceable SDK session holder, and passes it explicitly to `createProductionCanvasServerRuntime` and `createRadiusExtension`. The [server factory](../../packages/adapter-canvas/src/server.ts) owns its server container, coordinator map and owner-consuming route bindings; it reuses the authoritative route table and existing provider services. There is no default server singleton or global active-owner setter. Task records retain the operation ID, attachment instance ID, generation and promise. Each attachment retains its original transport URL/token, not another panel's transport.

**Retained inner scopes:** Moving storage does not make every operation globally single-flight. The shared scheduler still serves setup, deletion, verification retry, rollback, cleanup retry and exit-setup. Queueing remains per attachment and operation. Active-work and settlement queries remain keyed by instance ID, including same-ID replacement; the inherited operation-ID set is not a reference counter, so an old attachment settling the same operation can remove the ID while its replacement still runs. Generation metadata does not add provider-callback fencing.

| Work or claim                  | Scope and trigger                                                           | Release and shutdown predicate                                                                                                         | Transport                                      |
|--------------------------------|-----------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------|
| Delete resume                  | Attachment's task map; server-ready scan of unfinished deletions            | Latest task finalizer removes the entry; no new global recovery claim                                                                  | Existing deletion runner                       |
| Automatic rollback             | Attachment and operation; terminal rollback-pending recovery or finalizer   | Claim released after internal POST settles; no shutdown-admission check                                                                | Original attachment's rollback POST            |
| Provider reconciliation        | No global claim; server-ready scan or failed task with unresolved mutations | Existing recovery policy decides next task; repeated scans may queue repeated work                                                     | Original attachment's setup/cleanup runners    |
| Reconciliation timer           | Attachment and operation; failed task finalizer                             | Handle removed before callback; callback checks instance shutdown, operation presence, terminal state and unresolved mutations         | Original attachment's runners                  |
| Verification monitor           | Runtime and operation; eligible server-ready recovery                       | Claim released in monitor task `finally`; existing account/tracking/stop policy retained                                               | Original attachment's verify-status GET        |
| Verification acquisition retry | Same runtime monitor claim for acquisition-pending recovery                 | Released in the same `finally`; existing retry command and selected-account rules retained                                             | Existing retry runner and attachment transport |
| Finalizer follow-up            | Latest task in attachment/operation chain                                   | Clear execution state, remove task/active ID, notify listeners, then request rollback or reconciliation; no new blanket shutdown check | Original attachment                            |

**Lifecycle and deferred corrections:** Panel close retains active work's transport until settlement or the existing 46-minute bound. Reopen invalidates the prior deferred close through the existing close generation and server-entry checks. Closing an idle panel does not dispose the runtime owner. Shutdown marks each owned instance before requesting its stop, then preserves the bounded server/session cleanup phases without waiting for task completion or releasing resources still needed by settling work. Reconciliation callbacks still read the instance-ID shutdown marker; starting a replacement with the same ID clears it. Cancelling more timers, adding generation fences, globally deduplicating recovery, suppressing finalizer follow-ups after shutdown and identity-checking executor-map deletion are explicitly deferred behavior corrections, not guarantees of this extraction.

**Residual ownership at the task-owner boundary:** The selected-executor map, GitHub account coordinator and selection handles were left on their existing module binding for the [account slice below](#stage-2b-operation-bound-account-ownership). The operation registry, stores, provenance, locks, provider decisions, workflow observation and other unrelated caches/callbacks remain in their existing owners. Separate execution owners isolate bookkeeping, not operating-system keyrings or the process-wide operation registry. Disabled persistence (#506), cross-process recovery and exactly-once mutation guarantees remain outside this slice. The four local calls in the preparation inventory remain production dependencies; no setup tool, headless provisioning, provider-policy extraction or persisted runtime key ships.

**Checked-in evidence:** [Owner unit tests](../../packages/adapter-canvas/src/runtime/environment-execution-owner.test.ts) cover scoped chains/claims, independent owners, listener failure/unsubscription, replacement aggregation, timer release and late settlement. [Production coordinator characterization](../../packages/adapter-canvas/src/server-environment-execution.test.ts) exercises deletion, command queues, provider recovery, verification acquisition, missing-account refusal and post-shutdown finalizers through the real binding. [Runtime integration](../../packages/adapter-canvas/test/integration/runtime/environment-execution.test.ts) composes the real server and extension with a fake SDK for no-panel construction, close/reopen, wrong-instance close, replacement fencing, the exact deferred-close boundary, stop failure and bounded idempotent shutdown. [HTTP integration](../../packages/adapter-canvas/test/integration/http/environment-execution.test.ts) executes production legacy decoding/reconciliation and server-ready recovery, preserving operation IDs and quarantine while retaining authorization-before-parse. Existing operation controls, deletion, checkpoint/stop, setup/resume/account Chromium journeys and built-extension smoke remain required evidence.

**Test construction and compatibility:** Server consumers now construct explicit real-owner bindings, using [the shared test constructor](../../packages/adapter-canvas/test/support/server/production-runtime.ts) to select loopback OS-assigned ports and controlled identity preparation. The browser harness supplies its runner at construction through a fixture-local dependency; no mutable production test-runner setter remains. Pure helpers and the Stage 2A checkpoint forwarding exports remain unchanged. No lifecycle singleton compatibility exports remain. The new owner is pinned at 100% statements, branches, functions and lines; the admission pin, core/checkpoint gates and reliability registrations are retained, with ownership tests added to the scheduled selection.

**Release and rollback:** The ownership extraction preserves the intended scheduling, API and persistence behavior. The accompanying task error-reporting fix prevents an unobserved rejection when error reporting itself fails and is covered by a `radius` patch Changeset. Code/wiring rollback must account for active tasks and account restoration rather than treating shutdown timeout as completed remote cleanup. It must retain the preceding admission, checkpoint and stop safeguards.

## Stage 2B operation-bound account ownership

**Remaining limitations:** The context isolates executor maps, not the process-wide operation registry, `gh` identity/snapshot caches, operating-system keyring or cross-process activity. Contexts that share one keyring must share one coordinator. Token-backed calls retain their existing non-switching path; no new blanket account mutex is introduced. Registration still replaces by operation ID, and late finalizers still delete by operation ID without checking executor identity. Identity-fenced release, task generation fences, duplicate recovery and shutdown follow-up corrections remain separate work. **Owner and boundary:** Nell Shamrell-Harrington. This metadata-only prerequisite separates trustworthy transport evidence from the bounded retry decisions in Stage 1D2. Run/jobs and artifact bindings expose status and timing without changing account selection, producer contracts or the opaque log/download behavior.

**Transport evidence:** GitHub CLI's [`api.processResponse` at v2.98.0](https://github.com/cli/cli/blob/v2.98.0/pkg/cmd/api/api.go) writes `--include` status and headers before reporting HTTP errors. Its framing uses an LF status line and CRLF headers, with repeated values joined by commas. [`GetRun`, `GetJobs`, and `Run.ExportData`](https://github.com/cli/cli/blob/v2.98.0/pkg/cmd/run/shared/shared.go) show that the previous `gh run view --json` combined a run request, an unused workflow-name lookup, and paginated jobs before exporting JSON. Shared now issues explicit relative GET endpoints for run/jobs and artifact listings. It omits the unused lookup and never forwards an absolute pagination URL to the runner. Host/account resolution remains the injected runner's responsibility; no token extraction, HTTP client, debug logging, or credential policy is added.

**Metadata and result contracts:** Core's [`workflow-read-metadata.ts`](../../packages/core/src/workflow-read-metadata.ts) defines safe, adapter-independent evidence types. Shared's [`workflow-read-response.ts`](../../packages/adapter-shared/src/workflow-read-response.ts) parses actual status separately from command success and JSON validity. `WorkflowResponseMetadata` distinguishes `gh-api-include` from explicitly `unavailable`; `WorkflowReadTiming` distinguishes absent, invalid, delay milliseconds, and absolute deadline milliseconds. `Retry-After`, reset, receipt time, and server date remain separate evidence, not calculated retry permission. Secondary-limit messages may classify a 403 without timing headers, but never manufacture a deadline. SAML/permission evidence takes conservative authorization precedence. Arbitrary headers, response bodies, credentials, and pagination URLs are not public metadata.

`readWorkflowRunWithMetadata` adds complete/status-only/unavailable detail, phase evidence, and safe failure reasons; `readWorkflowRun` projects its existing `WorkflowRunRead | null` shape. `listWorkflowArtifactsWithMetadata` adds per-page evidence; `WorkflowArtifactReadError` retains existing error codes and typed evidence, and the legacy listing function projects only artifacts. Real status survives malformed JSON or a failed process, but neither becomes successful data. Selected authorization still throws the same shared `SelectedGhAuthorizationError` constructor and identity. Errors retain actionable host-redacted stderr and precise artifact-schema diagnostics without including response bodies in metadata. Host runners own credential redaction; Canvas artifact execution uses its existing credential redactor. Unexpected workflow-runner errors propagate. Deployment remains ambient; selected verification prepares and reuses its existing executor.

**One-shot bounds and deliberate differences:** A failed run GET receives no automatic reread. A known run survives unavailable/malformed/incomplete jobs without publishing partial jobs as complete evidence; nullable run/step conclusions keep gh's empty-string projection. Run plus all jobs pages share a monotonic 15-second allowance and 10 MiB cumulative captured UTF-8 stdout/stderr, with each command receiving the remainder. The underlying `maxBuffer` is per stream; the cumulative check is not a claim of a strict combined allocation cap. The maximum is 100 pages of 100 jobs, with verified continuation target and total-count completeness. Identity preparation is outside that primary allowance; a selected masked-404 repository probe is separately limited to 15 seconds/10 MiB. Deadline expiry aborts that subprocess and rejects late results, but does not add observation-stop semantics or cancel any workflow.

**Eligibility and retained behavior:** Run, jobs, repository probes, and artifact-list responses expose real metadata. Artifact listing keeps its one/five-page and 20-second-per-page bounds. Formatted logs retain 30 seconds/20 MiB and downloads retain 60 seconds plus bounded producer-file reads/cleanup; their additive metadata wrappers report `opaque-command`, not invented HTTP status. Control-plane evidence uses artifact listing plus opaque download, not another HTTP API. Artifact 403 still projects `GH_ARTIFACT_AUTH`, including rate limits, while the new metadata truthfully distinguishes authorization from rate-limit. This intentionally avoids enabling Canvas's existing graph rereads before Stage 1D2 owns their budget. TTL, single-flight, sequence isolation, generic delete-result downloads, primary error precedence, and terminal/repair ordering remain unchanged.

**Checked-in evidence and acceptance:** Owning response, budget, run, artifact, and direct observer tests cover framing, safe metadata, timing/header boundaries, exact commands, status versus exit code, selected/ambient identity, auth/masked-404 failures, pagination completeness, shared elapsed/output limits, timeout abort, and late completion/rejection. A real selected-executor/Canvas composition proves identity preparation is outside the primary allowance and cached for run/jobs. HTTP and outcome compositions preserve confirmed settlement and stop graph retries on legacy artifact 403. The controlled Chromium verification journey checks a confirmed run with rate-limited jobs still completes and makes exactly one run GET and one jobs GET. The scheduled reliability allowlist includes the new shared tests. New transport/budget modules and existing shared read/artifact modules have 100% four-metric coverage floors; unchanged repository/package floors are not lowered. Local browser prerequisites and unrelated Windows coverage failures must be reported separately rather than represented as passing candidate CI.

**Stage 1D2 boundary:** The preceding contracts describe the metadata-only prerequisite. The policy layer below adds bounded retries and observation-stop isolation and changes the legacy rate-limit 403 projection together with graph retry ownership. It does not change the producer schema, persistence format, account policy or Canvas/tool status vocabulary.

**Release assessment:** The released `radius` plugin receives a patch Changeset for avoiding immediate failed-run rereads and retaining a known run when jobs are unavailable. It does not claim automatic retries or Stage 1 completion.

### Stage 1D2 bounded read retry policy

**Delivery:** [#938](https://github.com/radius-project/ai-extensions/pull/938), [#939](https://github.com/radius-project/ai-extensions/pull/939), [#940](https://github.com/radius-project/ai-extensions/pull/940), [#941](https://github.com/radius-project/ai-extensions/pull/941), and [#943](https://github.com/radius-project/ai-extensions/pull/943) merged on October 2, 2026.

**Contract:** Terminal settlement validates the observed status before graph/progress reads or state changes, and the diagnostic collector receives that status through the same observation-bound log/control-plane ports. Unknown or nonterminal status never gets a synthetic completed fallback. An exact completed status with an unsupported nonblank conclusion exits before progress, heartbeat, graph or diagnostic reads. A blank conclusion retains bounded recovery; exhaustion after observing completion acknowledges completion without inventing an outcome. Completion memory belongs to the fixed-run monitor invocation, not a per-poll retry context. These exits preserve resource/diagnostic publication order, current-attempt guards and dispatch reservation ownership. Stage 1D2 does not complete Stage 1 or authorize later-stage extraction.

**Artifact integration:** The graph parser shares its scan budget across candidate starts and caps failed JSON parses. It may stop before recovering a later graph from sufficiently malformed output; retry integration does not expand that parser contract. Its adversarial worker resolves the retry-policy source and enables Node's TypeScript transformation for its parameter property; the four-second worker deadline remains unchanged. A shared-binding regression proves that a different application's malformed graph retires an older observer's accepted graph/progress/control-plane evidence, including after that observer refuses a newer flight's retry charges and a later deployment appears. Flight cleanup runs on rejection as well as fulfillment without clearing a newer flight. Canvas preserves its nullish application-fallback default while core/shared remain strict; explicit false still disables the Canvas fallback. These contracts do not reset retry credits, cooldowns or retirement generations.

**Core/shared boundary:** [`workflow-read-policy.ts`](../../packages/core/src/workflow-read-policy.ts) owns eligibility, timing conversion, the shared retry ledger, fixed elapsed deadlines and protected cooldowns through typed clock/cancellation ports. [`workflow-read-response.ts`](../../packages/adapter-shared/src/workflow-read-response.ts) executes the injected policy around each GET; [`workflow-read-budget.ts`](../../packages/adapter-shared/src/workflow-read-budget.ts) supplies production clocks and command/result/UTF-8 output bounds. Shared run/jobs and artifact bindings expose the same behavior to callers without Canvas. A direct caller retains one `createWorkflowReadSession` across automatic polls and supplies one observation context across its logical run/diagnostic collection; creating a new context is not permission to discard that session's cooldowns.

**Eligibility and admission:** Only actual framed HTTP 500/502/503/504 and genuine rate-limited 403/429 are eligible. Authorization, SAML/permission conflicts, selected masked-404 probes, invalid successful data, unsafe pagination, output truncation, opaque commands, unexpected runner rejection and mutations are not retried. The per-base-GET limit is three attempts; the enclosing observation has two additional GET admissions in total. Successful pages and legitimate producer-finalization observations are base work, not additional retry credits. Reservation is synchronous before sleeping, and cancellation or later deferral does not refund a reserved credit.

**Timing:** Ordinary eligible 5xx without an applicable timing header uses 500 ms then 1,000 ms backoff, plus an injected integer jitter from 0 through 250 ms. Jitter is added after the maximum of backoff and server constraints. Relative `Retry-After` starts at receipt. Absolute deadlines use the greater of receipt-relative delay and server-Date-relative delay plus one second for HTTP-date precision; without a trusted server date they defer rather than assume synchronized clocks. The latest applicable constraint wins. Invalid advertised timing never falls back to an earlier guess; missing/invalid required rate timing defers that endpoint for the observer lifetime. A wait equal to or greater than the remaining phase/enclosing time causes immediate deferral, not an early request or a useless wait. Wall-clock jumps cannot extend the monotonic elapsed budget.

An authentic secondary-limit message in a framed 403 or 429 establishes classification only. Shared selects the parsed error message and uses the same pure core predicate as its parser; core never imports a shared response type or interprets host diagnostics. A secondary limit requires usable `Retry-After`, even when primary remaining quota is zero: primary reset cannot prove that the secondary restriction ended. When primary quota is also exhausted, both valid constraints apply. Pure primary exhaustion retains reset-based timing. Successful JSON, log text and arbitrary CLI diagnostics cannot supply secondary timing.

**Retained cooldowns:** [`workflow-observation-scope.ts`](../../packages/adapter-canvas/src/server/services/workflow-observation-scope.ts) owns the Canvas instance's selected-executor identity and reader cache. Cooldowns key identity, target and endpoint family; pagination does not produce independent restrictions. They survive polling, ten-second payload TTL and the 32-reader LRU. The separate registry admits at most 32 protected endpoint-target restrictions per instance, not per identity. It fails closed with an explicit capacity diagnostic rather than evicting a restriction. Jobs deferral does not hide a readable run, accepted cached evidence or a confirmed outcome. Physical server stop ends the instance's read lifetime; normal refresh/focus does not erase a deadline. The existing environment-task deferred-close window is preserved: monitoring continues until physical stop, and reopening during that window reuses the same scope and restrictions. The independent environment-delete task retains its own read session across polls rather than constructing a new cooldown owner per GET.

The terminal bound accounts for three graph observations, forced progress and a possible control-plane refresh after workflow-log collection. TTL and immutable-ID caches usually remove most of that work; these ceilings never force downloads or sleeps. Terminal promotion retains the original elapsed clock and retry ledger instead of granting a fresh allowance. A known-run terminal collection never falls back to repository-wide discovery. Logs retain the 20 MiB output limit. Host identity preparation is not falsely described as subprocess cancellation; elapsed admission resumes against the remaining context after uncancellable host work returns. Local deadline fencing also does not claim that a filesystem cleanup or an uncooperative worker has finished.

**Artifact and subscriber ownership:** Core's [`deploy-artifact-evidence.ts`](../../packages/core/src/deploy-artifact-evidence.ts) retains a fixed flight budget and a per-observation candidate-download ledger. The flight deadline is independent of the admitting subscriber's deadline, while the retry ledger, endpoint cooldowns and identity remain shared. A joining subscriber cannot contribute fresh retries or extend the flight's deadline; its own earlier deadline/cancellation independently fences its result. Leaving one subscriber does not abort another's shared work. The instance or last subscriber may stop the flight, after which late completion cannot mutate accepted sequence, last-good evidence or payload cache. Graph/progress/control-plane convenience calls do not automatically repeat failed opaque downloads. Listing transport errors, authorization and malformed evidence stop the outer graph loop; only missing or unfinished producer evidence permits its existing finalization observations.

Each observation retains its original deadline and ledger across derived phase/cancellation contexts. Flight retry meters charge consuming subscribers through deduplicated receipts; an insufficient subscriber refuses that flight without cancelling a valid subscriber. That specific refusal survives same-observation TTL and convenience projections, while older evidence already accepted by the subscriber remains available unless a confirmed repository-wide absence retires it. A genuinely independent observation may consume already-settled accepted cache without commands, but cannot erase protected endpoint cooldowns. Attempted opaque downloads and received failure evidence stay with the observation, including across terminal promotion; no wrapper creates a fresh retry/download allowance. Receipt state is limited to existing observation, flight and cache lifetimes.

Workflow-run GETs without an explicit observation request remain one-shot. Retries require caller-owned observation context, so legacy polling cannot replenish retry credits on each call.

**Lifecycle and settlement:** Runtime close/shutdown use the server stop port. Monitor publication is fenced by instance and attempt; stopping observation never issues `gh run cancel`, retries a dispatch, or releases an in-flight dispatch's reservation before it actually settles. Shared execution forwards cancellation where supported and rejects late results. An opaque download's temporary directory remains until its worker actually settles; cleanup runs once and cannot replace its primary/auth failure. Confirmed workflow conclusions remain authoritative when graph or diagnostic evidence is deferred/exhausted. Resource settlement, diagnostics and `errorKind` precede publishing `failed`, because the status endpoint and tool can immediately trigger the existing repair path.

Physical stop completes in-flight verification, bypass and graph HTTP reads with 503 rather than leaving their sockets open. It stops local deployment monitoring and suppresses later automatic repair/notice handoff; it does not cancel the remote workflow. Before a deferred close reaches physical teardown, the existing monitor and callbacks remain active.

After a verification run is confirmed failed, a diagnostic-log timeout or output-limit failure does not change that outcome to unknown. The status route records an explicit unavailable-log notice, finishes and persists the tracked operation as `failed_partial`, and returns the existing failed response. Timeout includes both the 30-second log phase and admission refused by an exhausted enclosing observation deadline. Missing logs remain missing classification evidence: the limit notice is not parsed as workflow output and cannot enable bypass. Cancellation, stale-request fencing, selected-account authorization failures, unexpected errors and the bypass route retain their existing handling.

Verification-log limits are exercised through the real shared reader in deterministic unit and HTTP integration tests; the HTTP fixture supplies an actual observation scope so budgeting is active. The Chromium recovery journey checks the existing generic failed-response display, workflow URL, stopped spinner and elapsed display, and absence of bypass, rather than simulating a large command output or real timeout. The browser unit case "marks the panel failed with the run url when verification fails" asserts zero pending timers as the exact polling-stop contract. No browser production code, controls, response schema or visual layout changes are required.

**Evidence and release boundary:** Collocated policy, budget, artifact, scope, monitor and request tests own exact timing/admission and subscriber contracts. The real [HTTP deployment composition](../../packages/adapter-canvas/test/integration/http/deployments.test.ts) also routes the registered runtime status tool through a loopback status endpoint, retaining deferred/exhausted evidence without renaming a confirmed failed status. [Runtime contracts](../../packages/adapter-canvas/test/integration/runtime/runtime-contracts.test.ts) cover stop routing. The reliability allowlist includes new policy and lifecycle owners. A `radius` patch Changeset describes bounded recovery and truthful rate-limit uncertainty; internal packages remain ignored release units.

The scope's empty-iterator eviction guard is structurally unreachable while its map size exceeds 32; it remains defensive and unignored. The controlled Chromium verification recovery journey exercises production server wiring beyond local Node coverage. [deploy-artifacts.ts](../../packages/adapter-canvas/src/deploy-artifacts.ts) binds shared artifact reads and owns graph status/message projection. The [monitor](../../packages/adapter-canvas/src/server/services/deploy-monitor.ts) follows discovery/progress and calls the [outcome service](../../packages/adapter-canvas/src/server/services/deploy-outcome.ts). Those services still mutate Canvas state/resources. Existing core graph projection is reused rather than reimplemented.

**Attempt status versus resource status.** Canvas writes deployment-attempt `pending`, `in_progress`, `complete`, and `failed`; successful resource-level `CanvasGraphResource.deployStatus` is `success`. [summarizeDeployStatus](../../packages/adapter-canvas/src/deploy-tools.ts) passes through any nonempty attempt-status string; it does not validate a four-value enum. The tool/skill and TL-10 prose promising attempt `success` conflict with the actual terminal `complete`. Stage 3c owns only that tool-boundary correction, not a resource-status rename or Canvas change.

**HTTP contract (test-backed).** [handleDeployStatus](../../packages/adapter-canvas/src/server/routes/deployments.ts) serves `GET /api/deploy-status` as JSON with resource/log state, attempt, status, error context, timestamps, graph, workflow URL, active/repair flags, and handoff summary. `?since=` chooses incremental `logsNew` instead of the full `logs` field; indexes include the bounded buffer's base. The new terminal socket case verifies `complete`, attempt/run identity, timestamps, inactive state, and `panel-a` callback context. It does not claim to test all production wiring in `server.ts`.

**Tool contract (test-backed).** `radius_deploy_status` requires a selected Canvas server and reads its status route. It returns JSON text with `status`, `errorKind`, `deployRunUrl`, `startedAt`, `finishedAt`, and optional `diagnosticNote`/`diagnostic`. It drops `attempt`, `repairing`, `handoff`, `resources`, and `active`, and does not echo input `attemptId`. Falsy timestamps become `null`. Missing/stale entry returns a visible limitation; HTTP/transport failure returns a warning. Malformed JSON in a successful response currently becomes `pending`; that is baseline behavior, not a recommended error contract.

**Diagnostics (test-backed).** [fenceDeployDiagnostic](../../packages/adapter-canvas/src/deploy-diagnostics.ts) strips forged boundary lines and bounds agent-facing diagnostic text. Unit tests cover default/max log-tail behavior and fenced output. This is evidence for bounded/fenced diagnostics, not proof of complete secret redaction at every producer. Stage 1C supplies artifact identity/schema validation, Stage 1B preserves primary/secondary failure evidence, and the [acceptance audit](#stage-1-acceptance-audit) records the closure candidate's required redaction binding, forwarding inventory, executable boundaries, and qualification limits.

**Observation/error sequencing (test-backed).** Existing outcome tests verify graph success remains attempt `complete`, artifact retries stop on access denial, malformed graphs are not retained, failed-run diagnostics are published before terminal failure, a log-read failure retains the confirmed failed conclusion, and cancelled runs do not invent a Radius error. Monitor tests distinguish unconfirmed discovery/poll-cap outcomes from confirmed runs, continue on unavailable detail, and surface progress-read failure without stopping the deploy. Reader tests distinguish selected-account authorization loss from transient/rate-limit responses. These are the current guarantees, not a new workflow phase schema.

**Stage 1 evidence.** Reuse [reader tests](../../packages/adapter-canvas/src/deploy.test.ts), [monitor tests](../../packages/adapter-canvas/src/server/services/deploy-monitor.test.ts), and [outcome tests](../../packages/adapter-canvas/src/server/services/deploy-outcome.test.ts). New [summary unit cases](../../packages/adapter-canvas/src/deploy-tools.test.ts) cover attempt-status pass-through. The new [registered runtime case](../../packages/adapter-canvas/test/integration/runtime/runtime-contracts.test.ts) selects an older named attempt over a newer default, verifies the exact projected response, and proves no new panel/server acquisition or deploy request. It still uses an existing fake Canvas entry, so it is not a headless library demonstration.

## Repair, notices, and passive notification

**Behavior and ownership (source-traced; selected checks test-backed).** `GET /api/deploy-status` invokes `triggerDeployRepairHandoff` and `triggerDeployFailureNotice`; therefore polling `radius_deploy_status` can indirectly initiate agent work. The monitor completion path also invokes those triggers. The [server trigger functions](../../packages/adapter-canvas/src/server.ts) hold eligibility, delivery/retry, and attempt-state decisions; [runtime extension callbacks](../../packages/adapter-canvas/src/runtime/create-radius-extension.ts) connect them to the agent session. Run-unconfirmed failures use an informational notice rather than repair. Repair must remain bound to its snapshot/attempt budget.

**Passive endpoint.** `GET /api/deploy-notification` returns a smaller no-store payload: attempt/generation/run identity, status, application/environment, error, URL, repairing flag, and completion time. It does not include full resources/logs or initiate repair/notice delivery. The strengthened [HTTP notification case](../../packages/adapter-canvas/test/integration/http/deployments.test.ts) makes both callbacks throw if invoked. [Route unit tests](../../packages/adapter-canvas/src/server/routes/deployments.test.ts) and [server trigger tests](../../packages/adapter-canvas/src/server.test.ts) retain decision-level coverage.

**Lifecycle gap.** Trigger state and callbacks still depend on an entry and instance ID; closing/removing that entry is not an independent attempt lifetime. **Stages 3a/3b** own the attempt owner, explicit shared repair policy, and deduplication across tool/view observers. Read-only library observation in stage 1 must not inherit these side effects.

## Environment deletion and retry

**Admission (source-traced).** [handleDeleteEnvironment](../../packages/adapter-canvas/src/server/routes/environments.ts) owns `POST /api/delete-environment`: it validates target presence, rejects active deletion, fails closed on unreadable deployed-application checks or target discovery, blocks remaining applications, and refuses non-Azure providers. It durably registers an operation before background work and responds `202`; an existing conflict returns `409`, unsupported provider `400`, and unavailable preconditions `503`. Target discovery supplies immutable repository/tenant/client identity used later.

**Sequence (source-traced; test-backed ordering).** [runEnvironmentDeletion](../../packages/adapter-canvas/src/server/services/environment-deletion.ts) persists stages and heartbeat activity, confirms Radius environment teardown while credentials still exist, then performs provenance-checked federated credential cleanup, GitHub-environment deletion, and state-package deletion. App registrations remain in place. Provenance/live revalidation and the shared lock protect credential ownership; missing or unconfirmed evidence cannot authorize deletion. Failure to confirm the first stage stops later cleanup and returns partial failure. State-package failure remains retryable without replaying completed earlier stages.

**Persistence and interaction.** The existing operation record stores completed/unresolved stages; retry reopens that record and resumes unresolved work. Deletion has retry rather than setup's stop/continue/rollback controls. The frontend confirms the destructive request and presents retained-credential or partial-completion guidance. Shared helpers include [GitHub environment deletion](../../packages/adapter-canvas/src/server/services/github-environment.ts), also used by setup rollback, and [state-package deletion](../../packages/adapter-canvas/src/server/services/state-package-deletion.ts).

**Test-backed examples.** [Deletion runner tests](../../packages/adapter-canvas/src/server/services/environment-deletion.test.ts) assert ordering, lock scope, first-stage fail-closed behavior, unchanged/shared/unproven credential retention, live identity revalidation, missing package convergence, and retryable package failure. [Environment HTTP tests](../../packages/adapter-canvas/test/integration/http/environments.test.ts) own admission and [operation-control HTTP tests](../../packages/adapter-canvas/test/integration/http/operations-control.test.ts) own retry projection. **Stage 6** supplies the no-panel tool path and maps close/shutdown behavior before moving this policy.
