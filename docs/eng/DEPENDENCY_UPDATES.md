# Dependency updates runbook

This runbook is for whoever triages dependency pull requests, including the on-call engineer. It covers how Dependabot updates arrive and which dependencies need more than a passing CI run before they merge.

## How updates arrive

Dependabot is configured by [`.github/dependabot.yml`](../../.github/dependabot.yml). That file is synced from [`radius-project/.github`](https://github.com/radius-project/.github), so do not edit it here: changes are overwritten by the next sync. It opens one weekly pull request per ecosystem after a 7-day cooldown. Every npm version update lands in the single `javascript-deps` group, so one dependency that needs manual work blocks the whole group until someone completes that work.

## Triage a failing Dependabot pull request

1. Open the failing check and find the first assertion failure.
2. Match the failure to a row below and follow the linked section. If nothing matches, treat the failure as a normal regression in the updated dependency.
3. Check out the Dependabot branch, apply the required changes, and push them to the same pull request. Once someone else pushes to it, Dependabot stops rebasing that pull request; comment `@dependabot recreate` only if you want to discard your commits and start over.
4. Run [`pnpm changeset`](../../CONTRIBUTING.md#changesets) when the update changes a released package, as described in the section you followed.

| Failure                                                                                                    | Section                                                     |
|------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------|
| `@xyflow/react` version mismatch from `scripts/graph-vendor-styles.mjs` or `scripts/library-artifacts.mjs` | [React Flow](#react-flow-xyflowreact)                       |
| `THIRD-PARTY-NOTICES.txt` is missing a `===== name@version =====` marker                                   | [Bundled third-party notices](#bundled-third-party-notices) |

## React Flow (`@xyflow/react`)

`@radius-project/graph-react` pins `@xyflow/react` to an exact version on purpose. Two contracts depend on that version:

- **Vendored stylesheet.** `packages/graph-react/src/flow.css` is a scoped copy of React Flow's `dist/style.css`, generated by `scripts/graph-vendor-styles.mjs`. The generator refuses to run against any version other than the one last reviewed, so an unreviewed stylesheet can never ship.
- **Public styling hooks.** Hosts may style `.radius-graph__edge .react-flow__edge-path`, `.react-flow__controls`, `.react-flow__controls-button`, `.react-flow__background`, and the `--xy-background-pattern-color` custom property. An update that removes or renames one of them requires a graph-react major release. See [Styling contract](../../packages/graph-react/README.md#styling-contract) in the graph-react README for the full contract.

A grouped Dependabot update that bumps `@xyflow/react` fails **Tests, browser coverage and library candidates** and **Build radius dist** until you complete these steps:

1. Read the React Flow release notes between the old and new versions. Look for changes to the stylesheet, the supported class names above, node and handle markup, `Controls`, `Background`, and viewport behavior.
2. Replace the old version with the new one in each of these places:

   | File                                                                        | What to change                                                      |
   |-----------------------------------------------------------------------------|---------------------------------------------------------------------|
   | `packages/graph-react/package.json`                                         | The exact `@xyflow/react` dependency (Dependabot usually does this) |
   | `scripts/graph-vendor-styles.mjs`                                           | `REVIEWED_FLOW_VERSION`                                             |
   | `scripts/library-artifacts.mjs`                                             | The packed graph-react manifest assertion                           |
   | `packages/adapter-canvas/test/ci/library-artifacts.test.mjs`                | The synthetic graph-react manifest                                  |
   | `packages/adapter-canvas/test/integration/artifact/built-extension.test.ts` | The `@xyflow/react` and `@xyflow/system` notice markers             |
   | `packages/graph-react/README.md`                                            | The version named in the vendored stylesheet paragraph              |

   Read the new `@xyflow/system` version from `pnpm-lock.yaml`.
3. Regenerate the vendored stylesheet with `node scripts/graph-vendor-styles.mjs`, then review the `packages/graph-react/src/flow.css` diff. Confirm that every supported hook above still exists.
4. Run `pnpm run test:integration:libraries`, `pnpm run test:component`, `pnpm run build`, and `pnpm run test:integration:artifact`. If **Visual comparisons** then reports an intended rendering change, follow [Canvas visual baselines](../../CONTRIBUTING.md#canvas-visual-baselines).
5. Add a changeset for `@radius-project/graph-react`. Use `patch` when the supported hooks are unchanged, and `major` when one was removed or renamed.

The Headlamp qualification fixture (`scripts/fixtures/headlamp/package.json` and `TOOL_VERSIONS` in `scripts/fixtures/headlamp/contracts.mjs`) pins the host's own React Flow peer. It is checked only by the scheduled real-host qualification, so it does not need to change to unblock a pull request.

## Bundled third-party notices

`packages/adapter-canvas/test/integration/artifact/built-extension.test.ts` asserts an exact `===== name@version =====` marker in the built plugin's `THIRD-PARTY-NOTICES.txt` for each runtime dependency bundled into Canvas: `react`, `react-dom`, `@xyflow/react`, `@xyflow/system`, `dagre`, `graphlib`, `lodash`, and `yaml`. When an update changes one of those versions, **Build radius dist** fails until the marker changes too:

1. Run `pnpm run build` and open `.artifacts/radius/THIRD-PARTY-NOTICES.txt`.
2. Confirm that the new entry exists and that its license has not changed. A license change needs maintainer review before the update merges.
3. Update the matching marker in the test, then run `pnpm run test:integration:artifact`.
