# Conformance and Acceptance Matrix

The implementation must run shared semantic fixtures through core services and the App binding. The fixtures below are design requirements, not tests claimed to exist. No production CLI is required.

## Fixture Shape

Each fixture declares a stable ID, a typed lifecycle request, trusted fake caller context, explicit source/identity/execution responses, expected result/error, expected authorized side effects, and forbidden side effects. Inject clocks, IDs, cancellation, and external failures. Fakes throw on undeclared calls.

Schema tests validate both accepted and rejected messages. Service tests prove policy and transitions. App runtime/HTTP tests prove translation, identity propagation, errors, and lifecycle behavior using real production composition. Do not duplicate every service branch in Chromium.

## Repository Test-Policy Mapping

Use [the current test plan](../../../docs/design/2026-08-radius-canvas-test-plan.md) for inventories and status rather than inventing replacement requirement IDs.

- CA-05/CA-06 and RU-01 through RU-21 protect runtime declarations, source refs, handoffs, branch selection, host lifecycle, and registration. The new generic lifecycle tool adds a declared supported tool; it does not resurrect removed legacy tools.
- TL-02, TL-05, TL-07, TL-08, TL-09, TL-10, and TL-11 preserve existing tool contracts. Update intentional no-panel/read-only safety expectations explicitly rather than asserting old unsafe behavior remains.
- RF-01 through RF-09 and SU-01 through SU-18 protect actual route ownership, typed construction, response contracts, source access, credential/environment/deployment behavior, and operation projections.
- LC-10 through LC-17 protect worktree selection, remote reads, diff sources, handoff claims, failure propagation, repair identity, and setup resume behavior.
- CN-01 through CN-08 require an explicit cancel-or-continue policy, bounded process cleanup, stale-result fencing, and one cleanup outcome under races. Existing durable setup behavior must not be weakened by the new session registry.
- Changed material page states require their owning page/browser tests, HTTP state serialization tests, automated WCAG 2.2 A/AA checks, and keyboard coverage. Keep `renderPageState`/`readPageState` and stable IDs.

Every applicable row is cumulative. Unit tests target 100% changed-code coverage; existing aggregate/package/browser thresholds remain hard floors. Existing legacy untyped code is not a reason to introduce casts or success-shaped fallbacks into the new contract.

## Placement and Execution

Collocate service/adapter unit tests beside production modules. Put shared App conformance fixture data in `packages/adapter-canvas/test/fixtures/lifecycle`, and reusable test fakes in `test/support`; production code never imports them. Put cross-boundary tests in the existing runtime, HTTP, artifact, component, and e2e suites.

Core schema and pure policy fixtures remain in core's existing test locations so its tests do not depend on an adapter package. App conformance fixtures exercise those policies through controlled integration behavior, not copied production implementations.

The root coverage command already runs runtime/HTTP integration through package Vitest configurations. New tests in existing included directories need no new suite. Any new path excluded by a dedicated config must be explicitly added in the same implementation change.

Workflow/action changes require the shell helpers and uploader tests in `.github/workflows/extension-selftests.yml`. Template generation and artifact interpretation need paired fixtures; static substring assertions alone cannot prove exit propagation or completion semantics.

Visual and reliability evidence is scheduled rather than a PR shortcut or substitute. Real-host qualification is separately required before a qualified release; a fake SDK, loopback browser, or bundle smoke is not proof of actual host discovery or lifecycle behavior.
