# Conformance and Acceptance Matrix

The implementation must run shared semantic fixtures through core services and the App binding. The fixtures below are design requirements, not tests claimed to exist. No production CLI is required.

## Fixture Shape

Each fixture declares a stable ID, a typed lifecycle request, trusted fake caller context, explicit source/identity/execution responses, expected result/error, expected authorized side effects, and forbidden side effects. Inject clocks, IDs, cancellation, and external failures. Fakes throw on undeclared calls.

Schema tests validate both accepted and rejected messages. Service tests prove policy and transitions. App runtime/HTTP tests prove translation, identity propagation, errors, and lifecycle behavior using real production composition. Do not duplicate every service branch in Chromium.

## Authoring and Validation Checkpoint

- Standalone validation uses the shared captured-source executor, isolated Bicep build, the shipped validator's machine mode, and the fixed required/advisory policy. Missing required evidence stays incomplete; validation does not become authoring or deployment.
- Authenticated authoring is implemented through core operations/actions, the host-port agent bridge, actual proposal validation, and the existing promotion machinery. The current SDK cannot prove its required approval/assignment authority, so actual-host lifecycle authoring remains unavailable.
- The retained generation tool follows the selected writer: legacy selection preserves its usable bootstrap and modelability behavior; lifecycle selection never falls back on failure. A writer change during legacy discovery rejects the request instead of handing off or redispatching. Compatible readers and controls remain available through rollback.
- Direct CLI promotion has a real validation sequence that produces full original-input and validated-output evidence. The original command sequence creates its first seal through verification; explicit sealing is optional. An origin hash or caller-computed hashes alone cannot substitute for validation. Missing original baselines require a new run, not reconstructed approval or source history.
- The user approved retaining legacy compiler/static validation independently of canonical requirements. The repaired CLI preserves the original command sequence with actual verification and automatic first sealing; optional explicit sealing rejects subsequent input/output or record changes. This residual path retains legacy registry/cache behavior and git staging, not canonical runtime/Recipe evidence, host authority, or external-dependency isolation. Canonical authoring never falls back to it.
- T039-T050 are complete with actual runtime, executable, and built-artifact evidence. Deployment and observation have their own checkpoint below. The final gate totals and reproducible scenarios are in `quickstart.md`.

## Deployment and Observation Checkpoint

T051-T067 are complete with the runnable acceptance and same-source gate evidence recorded in `quickstart.md`. Configuration has its own completed checkpoint below; later repair, cancellation-control, and deletion work remains excluded.

- Core deployment accepts only a published definition with matching repository, environment, application, revision, and fresh trusted source-bound approval. The public approval reference conveys no authority. Canonical execution uses reviewed argument vectors, not caller shell text, and requires a preconfigured environment.
- The shared workflow binding verifies the selected dispatcher and both provider templates, immutable producer identity and audited producer bytes, and current protection evidence before consuming a one-shot dispatch preparation. Generic transport failures remain unconfirmed. Only bounded observation retries are permitted; reconciliation requires the exact operation, attempt, workflow, source, target, and initial run attempt.
- Final execution schema v1 and resource-progress schema v2 have paired strict readers. Progress cannot establish completion. Foreign identity, unsupported versions, conflicting sequences, contradictory outcomes, and unavailable final artifacts never establish stronger success. Confirmed workflow failure or cancellation remains independently authoritative.
- Executable shell tests run the actual checkout guard, restore body, command EXIT prologue, state save, cleanup, and finalizer. Restore failure blocks commands and save; command failure still permits save after successful restore. Save and cleanup failures remain separate, with fixed redacted diagnostics and publication after both phases.
- The real panel-free runtime, retained tools, and loopback HTTP binding exercise success, state-save failure, absent artifacts, foreign artifacts, cancellation, and uncertain dispatch. Each canonical scenario performs 100 reads without repair, redispatch, or source mutation. Runtime tools open no panels or servers; HTTP tests use the existing route container. The legacy HTTP regression independently performs 100 reads with zero repair.
- `operation.get` and `operation.list` observe session records only. Pagination is scope-bound; unavailable reads preserve uncertainty, and known canonical operations remain readable after writer rollback. No durable history, implicit retry, automatic repair, or rollback of deployed changes is promised.
- Browser states announce operation outcome independently from diagnostic availability, with fixed phase labels, polite live regions, keyboard dismissal, and WCAG checks. A failed workflow with missing detail stays failed rather than becoming an unconfirmed outcome.
- The current SDK has no trusted deployment approval seam. Its canonical mutation remains unavailable, while retained legacy deployment remains usable. Injected-host and artifact tests are not actual-host or live-cloud qualification, and no unqualified execution version is advertised.

## Test Placement and Execution

Collocate service/adapter unit tests beside production modules. Put shared App conformance fixture data in `packages/adapter-canvas/test/fixtures/lifecycle`, and reusable test fakes in `test/support`; production code never imports them. Put cross-boundary tests in the existing runtime, HTTP, artifact, component, and e2e suites.

Core schema and pure policy fixtures remain in core's existing test locations so its tests do not depend on an adapter package. App conformance fixtures exercise those policies through controlled integration behavior, not copied production implementations.

The root coverage command already runs runtime/HTTP integration through package Vitest configurations. New tests in existing included directories need no new suite. Any new path excluded by a dedicated config must be explicitly added in the same implementation change.

Workflow/action changes require the shell helpers and uploader tests in `.github/workflows/extension-selftests.yml`. Template generation and artifact interpretation need paired fixtures; static substring assertions alone cannot prove exit propagation or completion semantics.

Visual and reliability evidence is scheduled rather than a PR shortcut or substitute. Real-host qualification is separately required before a qualified release; a fake SDK, loopback browser, or bundle smoke is not proof of actual host discovery or lifecycle behavior.
