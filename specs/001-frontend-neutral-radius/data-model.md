# Data Model: Frontend-Neutral GitHub Radius

This is a domain and message model, not a database schema. New records have an injected App-session lifetime unless backed by existing setup storage or remote execution evidence. [Lifecycle contracts](contracts/lifecycle.md) define requests and results; [execution contracts](contracts/execution.md) define workflow evidence.

## Identity and Scope

| Entity            | Fields and identity                                                                                                  | Rules                                                                                                                                                 |
|-------------------|----------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------|
| Repository target | `repo` in `owner/name` form                                                                                          | Resolve through authorized repository access; normalize identity consistently before cache or authorization lookup                                    |
| Environment       | Repository, environment name, provider, identity references, recipe registrations, protection summary                | Repository plus environment identifies the selection; identity references are opaque, never raw credentials                                           |
| Application       | Repository, environment when deployed, application name; authored definition references and deployed evidence        | Application name alone is not globally unique; one authored definition is not evidence of a deployment                                                |
| Request           | `apiVersion`, `requestId`, `operation`, `target`, operation-specific `input`                                         | Request IDs correlate calls; they are not idempotency keys or authorization                                                                           |
| Operation         | Opaque `operationId`, operation kind, immutable resolved target/source, state, observations, attempts, actions       | IDs are generated by an injected service and never derived from a panel ID; reads still enforce target access                                         |
| Execution attempt | Opaque `attemptId`, parent operation, optional repaired operation/attempt, expected commit, provider, correlated run | Match identity as a tuple, not a sequence number alone; approved repair creates a new linked operation/attempt and does not reset the failed original |
| Caller context    | Trusted principal, repository/environment access, approved host action, scoped execution handles                     | Supplied outside public requests by the host/identity adapter; never deserialize authority from user input                                            |

An application may have definitions at several source revisions and observations from several operations. Keep them distinct. Discovery results carry separate authored/deployed evidence rather than merging by display name alone.

## Source Snapshot and Definition

`Source` is a tagged choice:

- `workspace`: `workspaceRef`, `branch`, `expectedFingerprint`. The reference resolves only through a host-authorized workspace registry.
- `git`: `ref`, `expectedCommit`. The commit is a full resolved object ID verified against the selected repository; mutable branch labels are not execution identity.

`ResolvedSource` records the actual repository, source kind, branch/ref, resolved commit where relevant, effective-input fingerprint, and resolution time. A workspace snapshot may include uncommitted changes; its base commit does not replace the fingerprint.

`DefinitionInput` records a normalized repository-relative path, file kind, content hash, and whether it existed at capture time. The input manifest includes the entry definition, referenced local modules and file inputs, effective configuration, and local custom-type/recipe artifacts. Generated scratch output is not an input merely because it is beside the definition. If the complete effective input set cannot be established, report incomplete validation rather than asserting an unchanged-source guarantee.

The implemented manifest policy is `github-radius/effective-inputs/v1`. Its fingerprint is `sha256:<64 lowercase hexadecimal digits>` over the exact UTF-8 bytes of canonical JSON containing the policy version, entry definition, and input records sorted by exact path without locale-dependent ordering. Each record contributes its path, kind, existence, and content hash; absent and empty files are distinct. Incomplete manifests have no fingerprint. Comparison checks the canonical records as well as the fingerprint, so stale fingerprint metadata cannot establish unchanged inputs. The shared adapter remains responsible for discovering the complete dependency closure and capturing the corresponding exact bytes.

The initial shared read adapter captures static local Bicep modules and load-file calls, the nearest applicable JSON configuration, and managed local custom-type/recipe artifacts. Bicep interpolation, dynamic dependencies, directory-enumeration functions, imports/using declarations, remote modules, non-Bicep modules, and configuration it cannot parse produce incomplete evidence instead of a complete snapshot. It excludes unrelated generated output and fetch metadata, rejects link aliases, and exposes only context-owned snapshot references. Source discovery, staging, promotion, and broader compiler-language support are not implied by this read adapter.

Discovery composes that adapter with authorized workspace and GitHub source hosts. It considers `.radius/app.bicep` before `app.bicep`, can return both canonical definitions, and explicitly reports partial rather than recursive discovery coverage. Remote capture verifies commit-pinned bytes and Git blob hashes and requires a complete tree of at most 256 regular files, 1 MiB per file, and 16 MiB total. Truncated trees, symlinks, and submodules are unsupported, not empty repositories.

Graph compilation additionally consumes owned captured binary bytes. A statically referenced local `.tgz` extension is a hashed input; the compiler, not closure discovery, validates its package contents. The managed `custom-types.tgz` name still requires its existing generated companion artifacts. Dependency checks follow the selected definition and its static compilation dependencies, not inert registry strings in captured recipe companions or loaded data. Genuine registry restoration and unsupported closures remain unavailable. Compilation uses a non-inheriting process environment and isolated home/cache without rewriting captured configuration or source. This isolates credentials from the compilation context; it is not an operating-system sandbox.

Path validation must reject absolute paths, parent traversal, drive/UNC escapes, encoded path tricks at transport boundaries, and symlink/junction targets outside the authorized root. Comparison and compilation use consistent copied input bytes; recheck the original input manifest under the promotion guard before replacing any managed file. A newly created or deleted input is a change, not an empty value.

`DefinitionProposal` contains an operation/action-bound staging reference, proposed output manifest, original input fingerprint, validation report, and promotion outcome. Output references must resolve within the authorized staging area; they are not arbitrary agent-supplied filesystem paths. Preserve existing rollback-on-write-failure behavior and staging cleanup instead of presenting a multi-file write as inherently atomic.

## Graphs and Observations

| Entity                 | Fields                                                                                                            | Interpretation                                                                                        |
|------------------------|-------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------|
| Graph result           | `kind`, canonical Radius graph, resolved provenance, environment when relevant, `observedAt`, observation quality | `authored`, `planned`, or `deployed`; no panel selection or layout coordinates in the canonical graph |
| Planned enrichment     | Recipe registrations and their provenance, expected resource outputs                                              | Use actual target registrations; not an authoritative cloud-provider execution plan                   |
| Graph diff             | `status: available`, base/head provenance, canonical difference                                                   | Both sources resolve independently; frontend presentation cannot redefine equivalence                 |
| Unavailable comparison | `status: unavailable`, affected base/head source, reason code, safe explanation                                   | Not an empty graph and not a successful no-change comparison                                          |
| Observation            | `quality: current/stale/unknown`, `observedAt` when known, evidence source, completeness, optional limitation     | Observation failure does not determine execution success or failure                                   |
| Paged discovery        | Items, optional opaque continuation token, scope, observation/coverage metadata                                   | A page with incomplete evidence must say so; cursors bind to caller scope and filters                 |

An empty, successfully inspected collection differs from an unavailable listing. An artifact's creation time does not establish that resources still have the same state now. `current` means the observation was successfully refreshed from its stated evidence source, not that an ephemeral control plane was continuously available.

## Validation Report

`ValidationReport` has `status: passed/failed/incomplete`, `checks`, source/proposal fingerprints, and redacted diagnostics. Each check contains stable `checkId`, `classification: required/advisory`, `status: passed/failed/unavailable/skipped`, reason, and optional location.

Classifications are set by the versioned validation policy before execution. Required checks include path and input-closure safety, required artifact consistency, type/recipe/schema checks, compilation, source references, and unchanged-source promotion preconditions. Authoring additionally requires supported application source; standalone validation does not require an agent.

Reduction rules:

1. A failed required check makes the report `failed`, even if other checks are unavailable.
2. With no failed required check, any unavailable or skipped required check makes the report `incomplete`.
3. All required checks passing permits `passed`; advisory failures or unavailable/skipped advisory checks remain visible warnings and cannot hide required failures.
4. Promotion additionally requires current authorization, valid output references, and an unchanged input manifest. A `passed` report for an older fingerprint does not authorize replacement.

Unsupported check execution is never silently converted to a passed check. Reports explain what ran and what did not; they do not imply live deployment verification.

## Operation Lifecycle

Public operation state is separate from observation quality. `queued` initially means accepted by the lifecycle service, not confirmed GitHub dispatch.

| Current state     | Allowed next state      | Required evidence or action                                                                  |
|-------------------|-------------------------|----------------------------------------------------------------------------------------------|
| `queued`          | `running`               | Local execution begins or the exact correlated remote run starts                             |
| `queued`          | `action_required`       | A concrete prerequisite requires an authorized user/agent response                           |
| `queued`          | `failed`                | Confirmed rejection or execution failure, not an observation timeout                         |
| `queued`          | `cancelled`             | Local cancellation is confirmed before dispatch, or remote cancellation is confirmed         |
| `running`         | `action_required`       | A declared prerequisite is reached without concealing a completed failure                    |
| `running`         | `succeeded`             | All required completion evidence agrees and confirms success                                 |
| `running`         | `failed`                | A required phase or the correlated workflow has a confirmed failure                          |
| `running`         | `cancelled`             | Execution cancellation is confirmed; cleanup details remain separate                         |
| `action_required` | `queued` or `running`   | Authorized response accepted and remaining preconditions checked                             |
| `action_required` | `action_required`       | One action completes but another prerequisite remains                                        |
| `action_required` | `failed` or `cancelled` | Confirmed prerequisite failure or authorized cancellation                                    |
| Terminal state    | Same state              | Read, reconciliation details, or rejected late response; never restart the original mutation |

Fast completion can skip intermediate observations: a known queued operation may be observed as terminal when a correlated completed run supplies the necessary evidence. A state reducer must permit that evidence-based transition without manufacturing unseen progress.

On missing or contradictory observations, retain the last evidenced state with `stale` or `unknown` quality and return the limitation. Do not automatically repeat the mutation. If a terminal record later has contradictory evidence, disclose it and mark the observation uncertain rather than silently rewriting an executed operation as a fresh one.

Cancellation has a separate `cancellationRequestedAt` and request outcome; setting it does not mean `state: cancelled`. The existing setup distinction between pausing local orchestration, cancelling a workflow, and rolling back infrastructure remains explicit.

## Required Actions and Approvals

`RequiredAction` contains `actionId`, parent `operationId`, action kind, authorized responder class, target/source binding, declared response schema or choices, and status. Supported initial kinds are `user.decision`, `user.authenticate`, `agent.author_definition`, and `agent.repair_definition`; host display text is not executable authority.

An action is `outstanding`, `accepted`, `rejected`, `expired`, or `superseded`. Only an outstanding action accepts a response. Acceptance and its guarded continuation occur once within the owning context; repeats return `ACTION_NOT_OUTSTANDING`, not another mutation. This is not a durable replay guarantee after restart.

`UserDecision` contains a declared choice and permitted input. `AgentOutcome` contains `completed/failed/cancelled`, authorized staged-output references for completion, and bounded redacted diagnostics for failure. The agent binding proves its authority through caller context. Agent completion cannot stand in for user approval, and a user decision cannot impersonate an agent.

`Approval` identifies the trusted policy decision, operation/action, target, and source fingerprint or commit where relevant. Approval handles are opaque references; the backend must still verify GitHub environment approvals through the execution adapter. Source-dependent approvals become invalid when source changes.

## Execution Evidence and Partial Results

`ExecutionEvidence` contains contract version, operation/attempt identity, repository, environment, application when relevant, actual commit, workflow/run/run-attempt identity, sequence, timestamp, phase outcomes, and evidence availability.

A phase outcome is `succeeded`, `failed`, `skipped`, `cancelled`, or `unknown`, plus an exit code when available. Phases include dispatch, checkout validation, restore, command execution, state save, and cleanup. `skipped` must carry a reason; it is not success. The workflow conclusion is observed independently from GitHub, not trusted solely from an artifact.

`DeletionPlan` identifies the application or environment target and explicit phase treatments for workloads, state packages, workflows, and identity. Each phase lists ownership/provenance, whether resources are shared, required permission/approval, and result. Shared resources are retained unless separate ownership and approval permit their deletion. A partial result lists completed, blocked, failed, and not-started phases with recovery guidance.

## Retention and Ownership

- Page close disposes page listeners and browser polling, not the owning session context.
- Runtime keepalive observes session-owned active operations even when no panel exists, using the existing injected host lifecycle seam; it must not depend on an active server entry.
- Local source reads and transient computations cancel when their owning request is cancelled; late results cannot update a newer source context.
- Accepted session-owned operations may continue across panel close while their identity remains in the session context or existing setup store. Remote workflows have their operation/attempt correlation persisted in run metadata and evidence.
- Session shutdown fences local continuations, cancels cancellable work, and closes owned resources. It does not promise to cancel or recover remote mutations.
- An operation missing from the current context is explicitly unavailable unless an existing supported evidence source can resolve it. General history, restart reconstruction, and cross-session action replay remain outside scope.
